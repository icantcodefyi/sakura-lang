`sakura mcp serve` runs the compiler as a [Model Context Protocol](https://modelcontextprotocol.io) server. An agent calls compiler functions directly instead of running shell commands and parsing their output.

The CLI, the language server (`sakura lsp`), and the MCP server are thin adapters over one Rust analysis library (`sakura_analysis`). They share diagnostic data for the same input. MCP returns JSON objects containing records and summaries; CLI `--json` emits [JSON Lines](/docs/agents/diagnostics), and LSP adapts diagnostics to its protocol.

## Client configuration

The server uses stdin/stdout. Set `command` to the installed executable; this JSON shape is for clients using `mcpServers`. Replace the absolute root below with your project directory. See the [client-specific setup](https://github.com/icantcodefyi/sakuralang/blob/main/docs/mcp.md) for Claude Code, Codex and Cursor.

```json
{
  "mcpServers": {
    "sakura": {
      "command": "sakura",
      "args": ["mcp", "serve", "--root", "/absolute/path/to/project"]
    }
  }
}
```

## Snapshots

Analysis works on an immutable **workspace snapshot**. `check` without a `snapshot` reads the workspace from disk. Analysis and patch results carry snapshot ids; information tools such as `compiler_info` do not. This makes results reproducible and lets the server detect stale edits: a patch built against an old snapshot conflicts instead of applying to the wrong text.

## Tools in v0

| Tool | Parameters | Returns |
| --- | --- | --- |
| `compiler_info` | none | `compiler`, `version`, `schema_version`, `edition`, `tools`, `features`, `workspace_root`, `manifest`, `lock_digest`. |
| `check` | `snapshot`, `paths`, `budget_ms` | Diagnostic and hole records, a summary and `over_budget` ([Diagnostics](/docs/agents/diagnostics)). |
| `symbol_query` | `name`, `id`, or `type_pattern` | Matching symbols with full signatures, including effect rows, error unions, and contracts. |
| `hole_context` | `snapshot`, `hole_id` | One [typed hole](/docs/agents/typed-holes) record. |
| `docs_query` | `topic` or `symbol`, `budget_tokens` | Documentation text within a token budget. |
| `explain_diagnostic` | `code` or `id` | The explanation for a code such as `V3001`, the same as `sakura explain`. |
| `format` | `snapshot`, `paths` | A patch with the canonical formatting. |
| `check_patch` | `snapshot`, `edits`, optional `frozen_specs` | Diagnostics for the patched code, plus the interface delta: which signatures the patch changes. |
| `apply_patch` | `snapshot`, `patch_id`, optional `frozen_specs`, `write` | A new snapshot, or a conflict. |
| `test` | `snapshot`, `selectors`, `seed`, `budget_ms` | Test results under deterministic handlers. |

`features.backends` lists the compiled backends (including `wasm` when present). `features.verify` reports CLI verification support together with solver status; a missing solver does not remove that capability. `features.test_execution` reports whether a test runner is configured. `sakura verify` is implemented in the CLI; MCP `verify`, `refactor` and `impact` tools remain planned.

`check.budget_ms` is a soft budget reported by `over_budget`. `test.budget_ms` is a wall-clock limit (60,000 by default, capped at 300,000). `docs_query` estimates tokens from bytes; its default budget is 1,500.

### Checking a patch before applying it

`check_patch` lets an agent try an edit without changing anything. The interface delta tells the agent, and the reviewer, whether the edit changes a public signature, effect row, or error union. `apply_patch` then commits it and returns the new snapshot.

**Frozen specs are opt-in on each call.** Pass `frozen_specs: "all"` (or comma-separated symbol names, including `permissions`) to both `check_patch` and `apply_patch`. The check returns `frozen_spec_violations`; application rejects changes to the selected signatures, effect rows, error unions, contracts, tests/properties and permissions with `V8020`. Use the original base snapshot when applying. Omitting `frozen_specs` does not enforce a prior check's freeze policy. The CLI compares against Git: `sakura check --frozen-specs all --since <baseline>`.

### Authority

Tools that execute code, such as `test`, run with capabilities issued by the host. A caller cannot name authority in a tool call. Tests run with deterministic default handlers and network access denied.

## Exporting your own functions as tools

**Planned:** compiler HTTP transport and function export are separate from the implemented stdio tools. `sakura mcp serve --tools a,b` would export functions from your program as MCP tools (design §11.2). `Tool.of` works in-process today; the export flag is not implemented.

A tool function is marked `@tool("description")`. Its parameters and result must be `Schema` types, and its error union must be made of `Schema` tags. This complete example checks the implemented in-process path; it does not start an MCP export:

```sakura
import std/tool.{Tool}

@tool("Return a greeting")
fn greet(name: String) -> String { "hello, {name}" }

pub fn main() -> Unit {
  let _tool = Tool.of(greet)
}
```

`Tool.of(greet)` builds a `Tool` value. Its JSON Schema comes from the parameter types, refinements included. When called, it validates the JSON arguments, runs the function under the caller's current handlers, and maps failures to a public `ToolError` with the tag name and payload. The same `Tool` values are used in-process by `Agent.run`, which takes them in the `tools` field of its `Agent` configuration record (see the [standard library](/docs/stdlib)).

In the planned MCP export, the model never supplies authority. The handlers installed by the serving program decide what `Http` can reach, and the manifest's `[permissions]` table is the ceiling.

## Stability

The stdio server, the ten tools above, their parameters, and the snapshot, content-hash and patch-id protocol are proposed as **stable from v0.2.0** under [draft RFC 0001](/docs/stability). **Planned before v0.2.0:** a tool that returns a CLI record, such as `symbol_query` or `hole_context`, returns exactly the `--json` record of the same name, `kind` included (design §17.242). Function export, HTTP transport and the `verify`, `refactor` and `impact` tools are not implemented and carry no promise.
