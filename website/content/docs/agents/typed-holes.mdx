A **typed hole** is a placeholder for code you have not written yet. You write it `?name`: a
`?` followed directly by a name, with no space. The compiler checks the rest of the program
around it and tells you what the hole needs: its type, the side effects allowed there, the
variables in scope and code that would fit.

This page is for agents, and the people guiding them, who build a program step by step instead
of writing a whole function and hoping it compiles.

## Writing a hole

```sakura holes
fn clamp(x: Int, lo: Int, hi: Int) -> Int
  requires ordered: lo <= hi
  ensures bounded: lo <= result && result <= hi
{
  ?body
}
```

`sakura check` accepts this program and reports one `hole` record. `sakura build` and `sakura run` reject it with `V2050`, so a hole cannot reach a build by accident.

The name is for you and for tooling. Use one that says what belongs there: `?body`, `?user`, `?retry_policy`.

`?` has a second use: after a `Result` value (`r?`) it gives the success value or raises the error as a failure (`Fail<E>`). The two never clash: `?` directly before a name is always a hole, and `?` after a value is always a raise.

## What a hole reports

`sakura check --json` writes one `hole` record per hole, each on its own line. For the `clamp` program above, saved as `src/main.sak`, the record looks like this, spread over several lines and with hashes shortened:

```json
{
  "schema_version": "1.0",
  "kind": "hole",
  "id": "h:5d0c8e2b1a7f4396",
  "name": "body",
  "snapshot": "sha256:…",
  "span": { "uri": "file:///…/src/main.sak", "content_hash": "sha256:…",
            "start_byte": 123, "end_byte": 128, "role": "primary" },
  "expected_type": { "render": "Int", "structured": null },
  "allowed_effects": { "render": "{}", "row": { "labels": [], "tail": null } },
  "locals": [
    { "name": "x", "type": { "render": "Int" } },
    { "name": "lo", "type": { "render": "Int" } },
    { "name": "hi", "type": { "render": "Int" } }
  ],
  "candidates": [
    { "expr": "x", "fit": "exact_local" },
    { "expr": "lo", "fit": "exact_local" },
    { "expr": "hi", "fit": "exact_local" },
    { "expr": "Int.min(?a, ?b)", "fit": "function" },
    { "expr": "Int.max(?a, ?b)", "fit": "function" }
  ],
  "contracts_in_scope": ["requires ordered: lo <= hi"]
}
```

A function candidate carries holes for its own arguments, named after its parameters, so filling the hole with it leaves smaller holes to fill next.

Every `hole` record has exactly these fields:

| Field | Meaning |
| --- | --- |
| `id` | `h:` plus a hash of the name, the file's content hash, and the span. Stable across runs while the text is unchanged. |
| `name` | The identifier after `?`. |
| `snapshot` | Hash of the workspace snapshot that was checked. |
| `span` | Where the hole is, in the same shape as a diagnostic span, with `role` `primary`. |
| `expected_type` | The type the hole must produce, fully solved where possible, as `{ "render", "structured" }`. |
| `allowed_effects` | The full effect row (the side effects allowed) at this point, as `{ "render", "row" }`. Effects already used elsewhere in the body are not subtracted. |
| `locals` | Every local in scope, innermost last, each with `name` and `type`. |
| `candidates` | Up to 10 ranked expressions that fit, each with `expr` and its `fit` kind. |
| `contracts_in_scope` | The refinements (limits on a type, such as `where it > 0`) and contracts (`requires` and `ensures`) assumed at this point. |

## How candidates are ranked

- Exact fits from locals come first.
- Then constructors and functions whose result type matches the expected type, such as `Int.min` or `Int.max` here. Each is tried on a throwaway copy of the type checker's state, so trying a candidate never changes what the checker has worked out.
- Candidates that would need an effect outside the allowed row are filtered out.
- At most 10 candidates are reported.

A hole never changes the inferred types of other variables; it only stands for its own unknown type. The rest of the body, including effects and contracts, is checked normally around it.

## Filling a hole

Following the report, an agent fills the hole:

```sakura
fn clamp(x: Int, lo: Int, hi: Int) -> Int
  requires ordered: lo <= hi
  ensures bounded: lo <= result && result <= hi
{
  if x < lo { lo } else if x > hi { hi } else { x }
}
```

The `ensures` clause is checked each time `clamp` returns normally. Only a build can drop that check, and only when [`sakura verify`](/docs/agents/verify) has proved it; `run` and `test` always keep it, and there is no `build --release` flag. A wrong fill triggers the defect `D021`, which blames `clamp`. See [verification](/docs/agents/verify).

## Narrower holes

A hole takes its expected type from context. An annotation gives a hole a type when the context does not:

```sakura holes
fn greet(name: String) -> Unit ! {Console, Clock} {
  let now: Instant = ?now
  Console.print("hello, {name}; it is {Instant.format_iso(now)}")
}
```

Here the report expects `Instant`, and `allowed_effects` is `{Console, Clock}`. A function such as `Clock.now` fits on both counts.

## Holes in the MCP server

The [MCP server](/docs/agents/mcp) has a `hole_context(snapshot, hole_id)` tool. It returns the same record for one hole, which is cheaper than re-checking the project. The compiler's tests require the editor language server, after the same edits, to report exactly the same bytes as `hole_context`.

## Recommended agent workflow

1. Write every signature the task needs: types, effect rows, `Fail<...>` unions, and contracts. Bodies are holes.
2. Run `sakura check --json`. Fix signature-level errors first; these are what a human reviews.
3. Write tests for the behavior the task asks for.
4. Fill holes one at a time, using `candidates`, `locals`, and `contracts_in_scope`. Re-check after each.
5. When no `hole` records remain, run `sakura test --json`, then summarize any signature changes for review.

`sakura test`, like `build` and `run`, rejects remaining holes with `V2050`, even in a function the tests do not call.
