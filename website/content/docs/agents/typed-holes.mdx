A typed hole is a placeholder for code you have not written yet. In Vow it is written `todo()`. A hole type checks anywhere, as any type, so a program with holes can be checked and tested before it is finished.

Holes turn "write the whole function and hope it compiles" into a sequence of small steps, each with precise feedback.

## Writing a hole

```vow title="src/users.vow"
type Email = String where is_email(it)
type Password = String where it.len >= 12
type SignupError = EmailTaken | Banned

fn signup(email: Email, pw: Password) -> User ! {Db, Clock, Random, Fail<SignupError>}
  ensures result.email == email
{
  if Db.exists(users, email) { fail EmailTaken }
  todo()
}
```

`vow check` accepts this program and reports one `hole` diagnostic.

## What a hole reports

```json
{
  "code": "H0001",
  "severity": "hole",
  "message": "hole of type `User`",
  "span": { "file": "src/users.vow", "start": { "line": 9, "col": 3 }, "end": { "line": 9, "col": 9 } },
  "expected": "User",
  "hole": {
    "expected": "User",
    "effects": "! {Db, Clock, Random, Fail<SignupError>}",
    "bindings": [
      { "name": "email", "type": "Email" },
      { "name": "pw", "type": "Password" }
    ],
    "facts": ["not Db.exists(users, email)"],
    "contracts": ["ensures result.email == email"],
    "candidates": [
      { "name": "User", "kind": "record", "signature": "User { id: Uuid, email: Email, created: Instant }" },
      { "name": "app/users.create_user", "kind": "function", "signature": "fn create_user(email: Email) -> User ! {Db, Clock, Random}" }
    ]
  },
  "fixes": [],
  "docs": "/docs/agents/typed-holes.md#what-a-hole-reports"
}
```

| Field | Meaning |
| --- | --- |
| `hole.expected` | The type the hole must produce. |
| `hole.effects` | The effects code in the hole may perform. Anything else is an error. |
| `hole.bindings` | Every name in scope, with its type. |
| `hole.facts` | Conditions known to be true at this point, from enclosing `if`s and matches. |
| `hole.contracts` | Contracts the value in the hole must satisfy. |
| `hole.candidates` | Functions and constructors whose result type fits, ranked. |

Candidates are ranked by how well they fit: exact result type first, then functions whose arguments can be filled from bindings in scope, then functions whose effects are within the allowed row. A candidate that would need an effect outside `hole.effects` is never listed.

## Filling a hole

Following the report, an agent fills the hole:

```vow
fn signup(email: Email, pw: Password) -> User ! {Db, Clock, Random, Fail<SignupError>}
  ensures result.email == email
{
  if Db.exists(users, email) { fail EmailTaken }
  let user = User { id: Uuid.new(), email, created: Clock.now() }
  Db.insert(users, user)
  user
}
```

## Holes with a type

A hole can also be narrower than its context, by giving it a type:

```vow
let created: Instant = todo()
```

This is useful when you know what a sub-expression should be but not how to compute it yet. The report then lists candidates for `Instant` given the effects allowed here: `Clock.now()` appears, because `Clock` is in the row.

## Holes and tests

A program with holes can run its tests. A test that reaches a hole fails with the hole's location and expected type. Tests that never reach it run normally.

```bash
$ vow test
ok    rejects short passwords
fail  duplicate email fails
      reached hole at src/users.vow:9:3 (expected `User`)
1 passed, 1 failed, 1 hole
```

This lets an agent work test by test: write signatures with holes, write tests, then fill the holes that the failing tests reach.

## Holes block release builds

```bash
$ vow build --target native
error  cannot build for release: 1 hole remaining
       src/users.vow:9:3  hole of type `User`
```

`vow check` and `vow test` accept holes. `vow build` for release does not. A hole can never reach production by accident.

## Recommended agent workflow

1. Write every signature the task needs, with effects, errors, and contracts. Bodies are `todo()`.
2. Run `vow check`. Fix signature-level errors first; these are the ones a human will review.
3. Write tests for the behavior the task asks for. They fail at holes.
4. Fill holes one at a time, using `hole.candidates` and `hole.bindings`. Re-check after each.
5. When `vow check` reports no holes and `vow test` passes, summarize any signature changes for review.

With the [MCP server](/docs/agents/mcp), the `hole` tool returns the same report for one hole by position, which is cheaper than re-checking the whole project.

## What the compiler checks

- `todo()` has whatever type its context requires, and performs no effects.
- Every hole is reported with its full context, so no hole is silent.
- The rest of the program is checked normally around holes, including effects and contracts.
- Release builds reject any remaining hole.
