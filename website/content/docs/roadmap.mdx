<Callout type="info" title="Where things stand">
  `0.1.0` is the published preview (2026-10-20), and `v1.0.0-beta.1` is next, a beta that may have bugs and is not for production. **M3 is complete** (signed 2026-10-18). **M4 is complete** (signed 2026-10-20, exit commit `dee11301`) and shipped in `v0.1.0`: the WebAssembly backend runs every corpus program the way JavaScript does, and `sakura verify` proves contracts with Z3. Native code generation (M5) is experimental. Changes on main after `0.1.0` are not in that package ([changes since 0.1.0](/docs/changes)). Releases have no dates.
</Callout>

The milestones run **M3 → M4 → M5**; [Toward 1.0](#toward-10) lists the releases. The [completion plan](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/m3-completion-and-m4.md) defines the gates; [design §17.81–§17.99](https://github.com/icantcodefyi/sakuralang/blob/main/docs/design.md) defines the provisional M4 decisions. M0–M2 provide the existing parser, type/effect checker, JS backend, handlers, typed holes, formatter and test runner.

## M3: finish the JS language and agent tooling

Working today:

- Runtime contracts and refinements, bounded compile-time literal evaluation (`V5004`, with `V5002` retired), refined-target `Untrusted.validate` (`V5003`) and collection-only `W5005`; opaque constructors and fields rejected outside their module with `V1006`; compiler-known prelude `Trust`, with `@trust("reason")` restricted to trusted sink arguments (`V6001`).
- Scoped capability/resource escape checks (`V6002`/`V6003`) and `V6001` for user externals receiving or constructing another package's capabilities or any handler.
- Std data, JSON schemas and codecs, SQLite and memory SQL, filesystem and file callbacks, HTTP, serving, CLI, structured tasks, budgets, tools and agent loops. `sql"…"` arguments use `SqlValue.from` conversions and become bound parameters.
- `Tool.of` on a named `@tool` function, `@llm` body generation, and effect-row parameters on types: `Tool<e>`, `Agent<T, e>`, `Router<e>`.
- `sakura new <cli|lib|agent|api> <name>`, `init`, LSP, compiler MCP, impact-aware fixes and frozen-spec checks. Analysis reuses unchanged modules' signatures and bodies; a private-body edit parses, lowers and checks only its module. Item collection, imports and exports remain global. Bodies reachable from a refinement predicate are part of the interface hash, so editing one invalidates reuse.
- [`sakura audit`](/docs/agents/audit), [`sakura doc`](/docs/agents/doc), [`sakura build --manifest`](/docs/agents/build-manifest), [`sakura test --record`](/docs/agents/cassettes) and `sakura test --contracts` (a generated property per contracted `pub fn`, `W7001` when it gives up).
- `Html.from` and nested `Html` templates; `Untrusted<T>` in `sql"…"` is a bound parameter, in `html"…"` escaped text and in `url"…"` a percent-encoded `UrlPart` (design §17.101, §17.124). `Http.recording`, `Llm.replay`, `Llm.recording` and `Test.fixtures` for offline cassettes, and streaming HTTP (`Http.stream`, `Http.read_chunk`).
- `sakura run` checks declared root permissions (exit 75 on denial) and passes `[permissions]` as `SAKURA_PERMISSIONS`; host handlers enforce filesystem, network and environment grants. This is not an OS sandbox for arbitrary JS or trusted FFI.
- Tests accept escaping typed failures and report them as failed tests. `Llm.anthropic` requests SSE and delivers one partial callback per text delta; local mock tests cover this, not a live-provider guarantee.

All twelve repository examples pass their current harness modes: seven run plus test (`hello`, `contracts`, `counter`, `typed_errors`, `word_count`, `graph`, `secrets`) and five test (`json_api`, `llm_extract`, `property`, `concurrency`, `agent_loop`). None is check-only. `llm_extract`, `agent_loop` and `secrets` replay committed **synthetic** cassettes with the test network denied. Their fixture READMEs describe provenance; this is not live-provider validation.

### M3 exit gates

The original M3 acceptance bar had eleven gates on the default branch on Ubuntu and macOS. The delegated security review has since closed M3. Commands are run in `compiler/` unless stated otherwise. These are acceptance requirements, not a claim that every command or flag is available today.

1. `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `cargo test --workspace --locked` pass with both `UI_MILESTONE` and `SEMANTICS_MILESTONE` at 3.
2. Two-way: every registered diagnostic except `V9999` and retired codes such as `V5002` is constructed by a crate or runtime, and every code constructed in `crates`, `runtime/js` or `runtime/rt` is registered. Every code a program can provoke from source has a passing UI fixture; `W8001` has one skipped by milestone, and `V9001`, `V8020` and the runtime-limit defects are covered by their own tests. Compare `grep -rhoE '\b[VWD][0-9]{3,4}\b' crates runtime/js runtime/rt --exclude-dir=sakura_diagnostics | sort -u` against the registry in both directions.
3. M3 acceptance tests cover contract blame (`m3.rs::m3_acceptance_contracts`, `D020`/`D010`), CLI exit 75, `tests/ui/V6003_route_handler_returns_file.sak`, stale/Unicode LSP replay matching MCP `hole_context`, and `recheck.rs` counters.
4. `cargo test -p sakura_cli --test examples`: all twelve examples execute in run or test mode, none only check. `llm_extract`, `agent_loop` and `secrets` replay committed cassettes with network denied.
5. `sakura test --std` passes; `std/INDEX.md` has no Planned section; `docs/llms.txt` has no remaining M3 items except `Sql.postgres` if the owner defers it.
6. CLI integration tests cover `sakura audit --json`, `sakura doc --search "fn(List<A>) -> Int"`, `sakura build --manifest`, `sakura test --contracts`, and `sakura test --record`.
7. `SAKURA_DIFF_PROGRAMS=2000 cargo test -p sakura_eval --test differential` passes with the expanded generator. Each of `parse`, `check`, `fmt_idempotent`, and `row_unify` runs clean via `cargo fuzz run <target> -- -max_total_time=600` on the gate-review day.
8. `cargo test -p sakura_fmt --test props` and the formatter corpus pass; `cargo test -p sakura_cli --test fmt_clean` passes: `sakura fmt --check` is clean on `std/`, `examples/`, `tests/semantics/` and `tests/ui/`, skipping `tests/fmt/`, parse-error fixtures and fixtures with a `// fmt: exempt covers <productions>` harness directive (not allowed under `std/` or `examples/`).

## M4: WASM and contract verification

M4 is complete: its exit commit `dee11301` was signed on 2026-10-20, the [instruction-count benchmark baseline](/docs/benchmarks) is blessed, and it shipped in `v0.1.0`. Working today:

- **WASM (W1/W2):** [`build`, `run` and `test --target wasm`](/docs/tour/memory#backends), with Node as the host. The [runtime ABI](https://github.com/icantcodefyi/sakuralang/blob/main/compiler/runtime/rt/ABI.md) defines bounded linear memory, conservative reference counting, persistent collections, frames, the trampoline and scheduler. LIR lowering makes continuations, closure environments, boxing and balanced `Dup`/`Drop` explicit; `sakura build --emit lir` writes it as text. The [ABI research](https://github.com/icantcodefyi/sakuralang/blob/main/research/09-m4-abi-and-encoding.md) records the design rationale.
- **Host operations:** HTTP sends and streams, SQLite, `Llm.stream`, `Serve.host()` and `Log.json()` run on WASM, including requests carrying `Secret` headers (`Http.bearer`, and `Llm.anthropic` over `Http.host()`), as approved by the security review (W0). Cassettes still never see a secret header's value. This is not live-provider validation.
- **Parity:** CI requires the JS/WASM matrix on Linux x64 and ARM64, Apple silicon and Intel macOS, and Windows x64 through `ci-required`. The harness compares the run/test semantics corpus and example runs for output, exits, defects and effect traces, including task numbers. Backend-specific expectations preserve the intentional JS safe-integer / WASM i64 differences. It also reports host-import coverage; local-server tests exercise network and serving operations outside the offline corpus.
- **Verification:** [`sakura verify`](/docs/agents/verify) runs pinned Z3 workers over Core obligations and reports `proved`, `disproved`, `unknown` or `unsupported`. cvc5 cross-checks `unsat` when installed. JS and WASM builds remove only eligible checks covered by matching authenticated proofs; other checks remain. Body edits invalidate the function's own proofs. See the [verification tour](/docs/tour/verification).
- **JS performance:** direct calls, bound handler dispatch, interval-proved arithmetic, owned updates and total-predicate `D011` bracket elision have landed in the WS-P work. `sakura build --dump direct`, `--dump core` and `--dump owned` expose compiler facts; the internal `--no-direct` switch exercises the CPS path. These optimizations do not establish the full performance acceptance bar or a WASM speedup.

Resumable JS loops, direct WASM calls for eligible local handlers and callbacks,
removal of total proved predicates, cached-verdict reuse and i64 counterexample
replay have landed. Tagged layout remains the baseline: `--emit lir --layout niche`
is refused. Native execution and Perceus reuse are experimental M5 work, not a
supported backend. The full performance acceptance bar is a separate gate:
[`bench/bench envelope`](https://github.com/icantcodefyi/sakuralang/blob/main/bench/README.md#m4-envelope-17213-2)
compares same-commit, same-host WASM runs with the matched native-language ports.
An advisory or incomplete report is not a pass. See [changes on main](/docs/changes)
and the [completion plan](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/m3-completion-and-m4.md).

### Agent development tools (DX0–DX7)

The compiler reports its capabilities through MCP. A downloadable skill, `sakura setup`, generated diagnostic references and eight offline cookbook projects are available. The first owner-approved agent-evaluation pilot ran 48 episodes for $4.20; its [report](https://github.com/icantcodefyi/sakuralang/blob/main/evals/agent-dx/reports/2026-10-18-pilot.md) records small-sample results and input-cap limits. Further evaluation and publication remain owner-controlled; release tooling is prepared. The VS Code client can be packaged locally and is not published. DX8 plugin packaging, the playground and Linguist submission remain planned; see the [agent DX plan](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/agent-dx.md).

For `scale(p, total) = total * p / 100`, proving `ensures result <= total` on normal return does not prove the multiplication cannot overflow. Overflow is a separate obligation. The wrong `/ 50` body has the counterexample `p = 100, total = 1`.

M4 excludes WasmGC, JSPI, typed continuations, WASI components, browser std support, threads, Perceus reuse/borrow inference, loop/recursion proofs, Float/String solver theories and proof certificates.

## M5: native code (experimental)

A Cranelift backend compiles the same LIR as the WASM backend to a native executable. It is **experimental and in no release**: it exists only in a compiler built from source with the Cargo `native` feature (`cargo build --release -p sakura_cli --features native`), where `sakura build`, `run` and `test` accept `--target native`. Release binaries are built without it.

On main, native agrees with JavaScript on every program of the semantics corpus, including direct-style calls, and runs `Json`, `Cli` and `Sql` on its own runtime. `Http`, serving, `Llm` and `WebSocket` are not ported yet: a program whose `main` declares one of them exits 75 at startup with "`Http` is not available on target `native`", and one that installs their host handlers itself stops with a `D090` defect at first use (exit 70). The sanitizer lanes that would make it safe to ship are still being built. See the [M5 plan](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/m5-native.md).

The current plan, pending the owner's confirmation, is that native gates no release: `--target native` ships as an experimental flag in the first minor release whose native test matrix is green. Borrow inference, Perceus-style in-place reuse, `W8001` copy diagnostics and region optimizations come after 1.0. No native performance claim is made.

## Toward 1.0

The order is set in the [road to 1.0](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/road-to-1.0.md). No release has a date; each tag is the owner's.

| Release | What it adds | State |
| --- | --- | --- |
| `v0.1.0-alpha.1` | M0–M3: the language, std, LSP, MCP, the skill, WASM and `sakura verify`, on npm, Homebrew and the release installer, for Apple silicon macOS and Linux x64 | published 2026-10-18 |
| `v0.1.0` | M4 exit, the first non-alpha preview: WASM complete, the web platform's byte, URL, header, form and crypto APIs in std, and Linux ARM64, Windows x64 and Intel Mac | published 2026-10-20 |
| `v1.0.0-beta.1` | A beta of 1.0, not for production: it may have bugs and may change before 1.0.0, and every breaking change until then is listed in the changelog with a migration. RFC 0001's machine contracts are intended from this tag; binary HTTP bodies, the `--json` summary split, web timers, streams, channels, URL patterns and WebSockets (all on main); the spec's grammar and diagnostics. A GitHub prerelease, npm under the `beta` tag and the Homebrew formula `sakuralang-beta` | planned |
| `v1.0.0` | Produced under the beta: seven consecutive clean nights of fuzzing ending at the tag, upgraded dogfood programs, agent evaluation results, the complete spec, signed macOS archives, and seven days after the last beta with no serious defect and no contract change | planned |

Not part of 1.0: packages (1.x), native as a stable target, Perceus reuse and borrow inference, crates.io publication, the playground and Linguist support.

## Decisions still open
