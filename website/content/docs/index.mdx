Sakura Lang is the programming language built for agents.

Most new code is now written by AI agents. Reviewing every line of that code does not scale, and the parts that matter most (what a function touches, how it can fail, what it guarantees) are usually invisible in mainstream languages. Sakura Lang is designed so that those parts are always written down, in one place, and checked by the compiler.

## The core idea

**The signature is the contract.** Humans review signatures. The compiler checks that the code does what its signature says.

A Sakura Lang signature states the inputs (with refinements), the output, every effect the function may perform, every way it can fail, and its `requires`/`ensures` clauses. The body cannot do anything the signature does not allow.

```sakura title="src/users.sak"
type Email = String where String.len(it) <= 254 && String.contains(it, "@")
type User = { id: Uuid, email: Email, created: Instant }

error EmailTaken(email: Email)
error Banned
type SignupError = EmailTaken | Banned

effect Users {
  fn email_exists(email: Email) -> Bool
  fn is_banned(email: Email) -> Bool
  fn insert(user: User) -> Unit
}

fn signup(email: Email) -> User ! {Users, Clock, Random, Fail<SignupError>}
  ensures result.email == email
{
  if Users.is_banned(email) { fail Banned }
  if Users.email_exists(email) { fail EmailTaken { email } }
  let user = User { id: Random.uuid(), email, created: Clock.now() }
  Users.insert(user)
  user
}

fn memory_users() -> Handler<Users> {
  handler Users {
    var users: List<User> = List.empty()
    fn email_exists(email) { List.any(users, fn(u) { u.email == email }) }
    fn is_banned(email) { false }
    fn insert(user) { users = List.push(users, user) }
  }
}

test "duplicate email fails" {
  with memory_users() {
    let _ = signup(Email.from("a@b.co"))
    expect_fail(fn() { signup(Email.from("a@b.co")) }, EmailTaken { email: Email.from("a@b.co") })
  }
}
```

Reading only the signature of `signup`, a reviewer learns that it:

- accepts only a string that satisfies the `Email` refinement,
- performs `Users`, `Clock`, and `Random`, and nothing else (no network, no file system, no environment),
- can fail only with `EmailTaken` or `Banned`,
- returns a user whose email is the one passed in. This `ensures` clause is checked at runtime on every return.

The test installs an in-memory handler for `Users`. `Clock` and `Random` need no handler in a test, because tests run under deterministic defaults (`Clock.fixed`, `Random.seeded`). No mocking library is involved: these are just different handlers for the same effects.

## Six pillars

**1. Effects you can see.** Every function type carries an effect row after `!`. Expected failure is the built-in `Fail<E>` effect over a union of `error` tags. There are no exceptions and no null. Defects such as overflow or a violated contract are not effects; they terminate the task. See [Effects](/docs/tour/effects) and [Handlers](/docs/tour/handlers).

**2. Memory without a borrow checker.** Every value has value semantics: no aliasable mutation, no reference cells, no cycles in the safe heap, no lifetimes. The JavaScript backend uses the host GC. The WebAssembly backend inserts reference counting at compile time and has no tracing GC; Perceus-style in-place reuse is planned after 1.0. Speed is a design goal, and no performance claim is made yet. See [Memory model](/docs/tour/memory).

**3. Contracts, always checked.** Refinement types (`where`), `requires`, and `ensures` are checked at runtime in every build. `sakura test --contracts` generates properties for eligible public functions and saves shrunk failures for replay. `sakura verify` asks the Z3 solver to prove individual obligations, and `sakura build` removes only the checks it proved. See [Contracts](/docs/tour/contracts) and [Testing](/docs/tour/testing).

**4. Secure by construction.** Effects are requirements; handlers are authority. The host supplies root handlers only for the std effects `main` declares, limited by `[permissions]` in `sakura.toml`, and code can only narrow that authority. `Untrusted<T>` marks outside data, `Secret<T>` cannot be shown or serialized, and tagged templates such as `sql"..."` never splice raw text. See [Capabilities and security](/docs/tour/capabilities).

**5. Built for agents.** A grammar that fits on one page, one way to do each thing, typed holes (`?name`), JSON Lines diagnostics with byte spans and fixes labelled by impact, specs frozen during agent repair, and a compiler MCP server. See [For Agents](/docs/agents).

**6. Batteries included.** One `sakura` binary for `new`, `check`, `build`, `run`, `test`, `verify`, `fmt`, `fix`, `audit`, `doc`, `setup`, LSP, and MCP (see the [CLI reference](/docs/cli)). The v0 standard library covers HTTP client and server, routing, SQL (SQLite first), JSON with derived schemas, CLI parsing, testing, and typed LLM calls with tools and budgets. See [Standard library](/docs/stdlib).

## Status

- **Design:** [docs/design.md](https://github.com/icantcodefyi/sakuralang/blob/main/docs/design.md) is the authoritative v0 design. Anything it does not specify is not in v0.
- **Compiler:** a Rust workspace in [compiler/](https://github.com/icantcodefyi/sakuralang/tree/main/compiler). It checks the whole language and runs it on JavaScript (the default) and WebAssembly, which agree on the test corpus. `sakura verify` proves contracts with Z3. Native code generation through Cranelift is experimental and in no release.
- **Releases:** `0.1.0-alpha.1` is published on npm, Homebrew and GitHub. It has no compatibility promise; [Stability](/docs/stability) describes what is proposed to become stable at v0.2.0.
- **Code on this site** follows the v0 design. The repository examples have executable coverage; planned features are labeled and the roadmap records remaining gates. These docs track main; [changes since alpha.1](/docs/changes) need a source build until the next release.

The [roadmap](/docs/roadmap) lists every milestone, M0 to M5.
