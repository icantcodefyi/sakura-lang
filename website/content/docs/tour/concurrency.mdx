Sakura Lang has no `async`/`await` keywords and no `Async` effect. Every Sakura Lang function may suspend, and nothing in application code can observe whether a call did. Suspension is a property of **handlers**: `Clock.sleep` suspends under the host clock and returns immediately under `Clock.fixed` (design §5.6).

Running work concurrently is a different matter. That uses the `Task` effect from `std/task`, which is in the prelude.

## The `Task` effect

This is a declaration or context-dependent excerpt, not a standalone program.

```sakura fragment
// std/task
pub type Scope          // external, scoped
pub type Fiber<T>       // external, scoped, affine
pub effect Task {
  fn scope<T, e>(body: fn(Scope) -> T ! e) -> T ! e
  fn spawn<T, e>(s: Scope, body: fn() -> T ! e) -> Fiber<T> ! e
  fn join<T>(f: Fiber<T>) -> T
  fn all<T, e>(bodies: List<fn() -> T ! e>) -> List<T> ! e
  fn race<T, e>(bodies: List<fn() -> T ! e>) -> T ! e
  fn yield_now() -> Unit
  fn cancel<T>(f: Fiber<T>) -> Unit
  fn cancelled(s: Scope) -> Bool
}
pub fn host() -> Handler<Task>
pub fn deterministic(seed: Int) -> Handler<Task>
pub fn every<e>(period: Duration, body: fn(Int) -> Bool ! e) -> Unit ! {Clock, Task | e}
pub fn par_map<A, B, e>(xs: List<A>, f: fn(A) -> B ! e) -> List<B> ! {Task | e}
```

`Scope` and `Fiber<T>` are external types: the host runtime owns their representation and user code cannot construct them. A function that uses these operations has `Task` in its row. The child bodies' rows flow into the caller's row through `e`.

## Scopes

`Task.scope` opens a scope. `Task.spawn` starts a child in it and returns a `Fiber<T>`. `Task.join` waits for the child's result.

```sakura
import std/http.{Http, RateLimited}
import std/response.{HttpError, Response}
import std/url.{Url}

fn load_both(a: Url, b: Url) -> (Response, Response) ! {Http, Task, Fail<HttpError | RateLimited>} {
  Task.scope(fn(s) {
    let fa = Task.spawn(s, fn() { Http.get(a) })
    let fb = Task.spawn(s, fn() { Http.get(b) })
    (Task.join(fa), Task.join(fb))
  })
}
```

Children never outlive their `Scope`. This gives three rules:

- **Failure propagates.** If a child fails or defects, the scope cancels its siblings, joins them, and propagates the first failure. Other failures are attached as `suppressed` in the outcome.
- **Defects are observed, not caught.** `Task.scope` observes a child's defect as `Outcome.Defect(info)`. `try` cannot catch it (design §5.4).
- **Resources are released.** A `Fiber<T>` is a resource: affine and bound to its scope (design §8.4).

`Task.all` runs a list of thunks and returns their results in order. `Task.race` returns the result of the first to finish. `Task.par_map`, a function of the `std/task` module, maps in parallel:

```sakura
import std/http.{Http, RateLimited}
import std/response.{HttpError, Response}
import std/url.{Url}

fn fetch_all(urls: List<Url>) -> List<Response> ! {Http, Task, Fail<HttpError | RateLimited>} {
  Task.par_map(urls, fn(u) { Http.get(u) })
}
```

## Cancellation is cooperative

A cancelled task stops at its next effect operation or at `Task.yield_now()`. Pure loops are not interruptible. A long pure computation that should respond to cancellation calls `Task.yield_now()` now and then:

```sakura
fn total_size(chunks: List<List<Int>>) -> Int ! {Task} {
  var total = 0
  for chunk in chunks {
    Task.yield_now()
    total = total + List.sum(chunk)
  }
  total
}
```

## Timers: `setTimeout`, `setInterval` and `clearTimeout`

There are no timer ids. A web timer is a fiber or a loop in a scope:

- `setTimeout(work, d)` is a fiber that sleeps first, `Task.spawn(s, fn() { Clock.sleep(d); work() })`; `queueMicrotask` is `Task.spawn` without the sleep.
- `clearTimeout` (and `AbortController.abort`) is `Task.cancel(f)`. The fiber unwinds through its finalizers before `cancel` returns, and it is used up: a later `Task.join(f)` is the defect `D095`. Cancelling a finished fiber does nothing else.
- `setInterval(work, period)` is `every(period, body)` from `std/task`. Ticks never overlap: a tick that comes due while `body` runs is skipped, and the next call receives how many were skipped. `clearInterval` is `body` returning `false`, or `Task.cancel` of the fiber running the loop.
- `AbortSignal.aborted` is `Task.cancelled(s)`: whether a child of `s` failed, so the scope is cancelling the others.
- `performance.now()` and `console.time` are `Clock.monotonic_micros()`, microseconds on the monotonic clock.

```sakura
import std/task.{every}

fn heartbeat() -> Unit ! {Clock, Console, Task} {
  Task.scope(fn(s) {
    let reminder = Task.spawn(s, fn() {
      Clock.sleep(Duration.seconds(30))
      Console.print("still working")
    })
    every(Duration.seconds(1), fn(skipped) {
      if skipped > 0 { Console.print("{skipped} ticks skipped") }
      Clock.monotonic().to_millis() < 10_000
    })
    Task.cancel(reminder)
  })
}
```

Under `Clock.virtual()` the ticks are reproducible, so a test can check what `heartbeat` prints without waiting.

## Handlers in child tasks

Children inherit the handler environment at spawn time. A handler's `var` state is accessed serially, so two children performing the same effect go through the same instance one operation at a time (design §5.5).

## No data races

Values have value semantics and closures capture by value (design §8.1). There is no shared mutable memory, so data races cannot occur. Tasks communicate through their results (`join`, `all`, `race`), through handler state, and through bounded channels.

## Channels

`std/channel` is `MessageChannel` inside one program. `with_channel(capacity, body)` gives `body` a `Sender` and a `Receiver` for a queue of at most `capacity` items: `send` waits while it is full, `try_send` fails `Full` instead, and `recv` waits while it is empty and returns `None` once the channel is closed and drained. Both ends are resources, so neither can leave the callback (`V6003`), and the channel is closed when the callback returns.

```sakura
import std/channel
import std/channel.{Receiver, Sender}

fn sum_of_squares(n: Int) -> Int ! {Task} {
  channel.with_channel(4, fn(tx: Sender<Int>, rx: Receiver<Int>) {
    let results = Task.all([
      fn() {
        for i in List.range(0, n) { let _sent = tx.send(i * i) }
        tx.close()
        0
      },
      fn() {
        var total = 0
        var more = true
        while more {
          match rx.recv() {
            Some(x) => { total = total + x },
            None => { more = false },
          }
        }
        total
      },
    ])
    results[1].unwrap_or(0)
  })
}
```

The producer runs at most four items ahead of the consumer. Under `Task.deterministic(seed)` the interleaving is the same on every run and every backend. A program in which every task waits, such as a `recv` that no `send` or `close` will answer, ends with the defect `D090` instead of hanging. `Source.buffer(src, capacity, body)` and `Source.tee(src, max_lag, body)` from `std/stream` are built on channels. The source their `body` receives, like the one `decompress_source` hands its body, is `Done` once that callback returns, so read it inside the callback.

Logical races with the outside world, such as two tasks reading and then writing the same database row, are still possible. The type system does not prove their absence.

## Detached work

There is no fire-and-forget spawn and no detached work in v0: every fiber belongs to a scope. A supervisor for long-running work is deferred (design §16.14). A capability, or a handler that captured one, may not flow into a `Task.spawn` closure whose scope outlives the `with` that produced it (`V6002`).

## Timeouts, retries, and budgets

All three are ordinary std functions over thunks (design §5.9):

This is a declaration or context-dependent excerpt, not a standalone program.

```sakura fragment
// std/retry
type Policy<E> = { retry_on: fn(E) -> Bool, max_attempts: Int, backoff: Duration, jitter: Bool, deadline: Option<Duration> }
fn policy<E>(retry_on: fn(E) -> Bool, max_attempts: Int) -> Policy<E> requires max_attempts >= 1
fn retry<T, E, e>(p: Policy<E>, action: fn() -> T ! {Fail<E> | e}) -> T ! {Clock, Random, Fail<E> | e}
// std/task
error Timeout(limit: Duration)
fn timeout<T, e>(limit: Duration, action: fn() -> T ! e) -> T ! {Clock, Task, Fail<Timeout> | e}
// std/budget: a handler, not a wrapper function
type Limits = { tokens: Option<Int>, usd: Option<Float>, calls: Option<Int> }   // None = unlimited
fn limits(l: Limits) -> Handler<Budget>
```

- `retry` starts a **new invocation** per attempt. It never resumes a failed one. `retry_on` is a pure predicate over the action's error union `E`, which is why `Policy` takes the error type as a parameter. `retry.policy(retry_on, max_attempts)` builds a policy with default backoff; the record fields can also be set directly. The first retry waits `backoff`, each later wait doubles, `jitter` randomizes the wait, and `deadline` bounds the total time. When attempts run out, the last error propagates; no extra "exhausted" tag is added. The std HTTP client refuses to retry non-idempotent methods without an idempotency key.
- `timeout` cancels the action's task at its next effect operation, joins it, then fails with `Timeout { limit }`. Finalizers run. `std/task.Timeout` is the only timeout tag in std; `LlmError` reuses it.
- `Budget` is an effect with `reserve` and `settle`. `Llm` and `Http` handlers consume it when it is installed. Exceeding it fails with `BudgetExceeded`, whose `kind` is `Tokens`, `Usd`, `Calls`, `Bytes`, or `Time`. Child tasks inherit the budget, split atomically.

A complete retry function, adapted from design §15.10:

```sakura
import std/http.{Http, RateLimited, Matcher}
import std/response.{HttpError, Response}
import std/url.{Url}
import std/retry.{Policy, retry}
import std/task.{Timeout, timeout}

fn fetch_both(a: Url, b: Url) -> (String, String) ! {Http, Task, Clock, Random, Fail<HttpError | RateLimited | Timeout>} {
  let policy: Policy<HttpError | RateLimited> = Policy { retry_on: fn(e) { match e { RateLimited { .. } => true, _ => false } },
                        max_attempts: 3, backoff: Duration.millis(200), jitter: true, deadline: None }
  timeout(Duration.seconds(5), fn() {
    Task.scope(fn(s) {
      let fa = Task.spawn(s, fn() { retry(policy, fn() { Response.text(Http.get(a), 1_000_000).trust(@trust("display only")) }) })
      let fb = Task.spawn(s, fn() { retry(policy, fn() { Response.text(Http.get(b), 1_000_000).trust(@trust("display only")) }) })
      (Task.join(fa), Task.join(fb))
    })
  })
}
```

A budget is installed as a handler and configured with a `Limits` record. From `main` in design §15.7:

This is a declaration or context-dependent excerpt, not a standalone program.

```sakura fragment
let limits = Limits { tokens: Some(20_000), usd: Some(0.50), calls: None }
with Llm.anthropic(key, Model.of("claude-sonnet-5-5")), Budget.limits(limits) {
  let t = extract_ticket(Untrusted.of("Login page 500s since 9am, blocking all customers"))
  Console.print("{t.priority}: {t.title}")
}
```

## Determinism

Evaluation is strict and left to right, arguments before the call. `Map` and `Set` iterate in insertion order on every backend. `Clock`, `Random`, and `Task` are effects, so a test can replace all three (design §8.7):

```sakura context=fetch-both
test "deterministic under virtual time" {
  with Http.scripted([(Matcher.Any, Response.status(200, "x"))]), Clock.virtual(), Random.seeded(1), Task.deterministic(1) {
    expect_eq(fetch_both(Url.from("https://a"), Url.from("https://b")), ("x", "x"))
  }
}
```

Under `Task.deterministic(seed)` scheduling is reproducible. `Clock.virtual()` advances only when told to. This is how `with` doubles as Sakura Lang's deterministic-simulation mechanism. See [Testing](/docs/tour/testing).

## Runtime model

The first backend compiles to JavaScript with a CPS trampoline and is single-threaded. A live host handler, such as `Clock.sleep` or `Http.send`, suspends by returning a step the driver awaits (design §13.3). The experimental native backend targets single-thread execution; worker threads and cross-thread atomic reference counting are not a current guarantee.

## Not in v0

- An `Async` effect, `async`/`await`, or colored functions (design §5.6).
- Durable workflows. They are a later official package, not part of the language (design §1.1, §11.3).
- Actors. `spawn` and `actor` are reserved keywords (`Task.spawn` is legal because a reserved word is accepted after `.`).
- Detached or supervised tasks, and timer ids (`setTimeout` is a fiber, above).
- Shared mutable state or locks in user code.

## What the compiler checks

- Code that uses `Task` operations declares `Task` in its row (`V3001` otherwise).
- Child rows flow into the parent's row through the `e` variables of `Task`'s operations.
- A capability or capturing handler does not escape into a task that outlives its scope (`V6002`).
- A `Fiber<T>` does not outlive its scope.
- A channel's `Sender` or `Receiver` is not returned from `with_channel`'s callback or kept in handler state (`V6003`).
