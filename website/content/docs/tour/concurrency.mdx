Vow has no `async`/`await` keywords and no `Async` effect. Every Vow function may suspend, and nothing in application code can observe whether a call did. Suspension is a property of **handlers**: `Clock.sleep` suspends under the host clock and returns immediately under `Clock.fixed` (design §5.6).

Running work concurrently is a different matter. That uses the `Task` effect, which is in the prelude.

## The `Task` effect

```vow
effect Task {
  fn scope<T, e>(body: fn(Scope) -> T ! e) -> T ! e
  fn spawn<T, e>(s: Scope, body: fn() -> T ! e) -> Fiber<T> ! e
  fn join<T>(f: Fiber<T>) -> T
  fn all<T, e>(bodies: List<fn() -> T ! e>) -> List<T> ! e
  fn race<T, e>(bodies: List<fn() -> T ! e>) -> T ! e
  fn yield_now() -> Unit
}
```

A function that uses these operations has `Task` in its row. The child bodies' rows flow into the caller's row through `e`.

## Scopes

`Task.scope` opens a scope. `Task.spawn` starts a child in it and returns a `Fiber<T>`. `Task.join` waits for the child's result.

```vow
fn load_both(a: Url, b: Url) -> (Response, Response) ! {Http, Task, Fail<HttpError>} {
  Task.scope(fn(s) {
    let fa = Task.spawn(s, fn() { Http.get(a) })
    let fb = Task.spawn(s, fn() { Http.get(b) })
    (Task.join(fa), Task.join(fb))
  })
}
```

Children never outlive their `Scope`. This gives three rules:

- **Failure propagates.** If a child fails or defects, the scope cancels its siblings, joins them, and propagates the first failure. Other failures are attached as `suppressed` in the outcome.
- **Defects are observed, not caught.** `Task.scope` observes a child's defect as `Outcome.Defect(info)`. `try` cannot catch it (design §5.4).
- **Resources are released.** A `Fiber<T>` is a resource: affine and bound to its scope (design §8.4).

`Task.all` runs a list of thunks and returns their results in order. `Task.race` returns the result of the first to finish. `List.par_map` maps in parallel:

```vow
fn fetch_all(urls: List<Url>) -> List<Response> ! {Http, Task, Fail<HttpError>} {
  List.par_map(urls, fn(u) { Http.get(u) })
}
```

## Cancellation is cooperative

A cancelled task stops at its next effect operation or at `Task.yield_now()`. Pure loops are not interruptible. A long pure computation that should respond to cancellation calls `Task.yield_now()` now and then:

```vow
fn total_size(chunks: List<List<Int>>) -> Int ! {Task} {
  var total = 0
  for chunk in chunks {
    Task.yield_now()
    total = total + List.sum(chunk)
  }
  total
}
```

## Handlers in child tasks

Children inherit the handler environment at spawn time. A handler's `var` state is accessed serially, so two children performing the same effect go through the same instance one operation at a time (design §5.5).

## No data races

Values have value semantics and closures capture by value (design §8.1). There is no shared mutable memory, so data races cannot occur. Tasks communicate through `Channel<T>` (bounded; `send` and `recv` are `Task` operations) and through handler state. The full `Channel` API is not yet specified in design.md.

Logical races with the outside world, such as two tasks reading and then writing the same database row, are still possible. The type system does not prove their absence.

## Detached work

There is no fire-and-forget spawn. Work that must outlive its caller needs `Task.Supervisor`, a capability obtained only from `main`'s root handlers. A capability, or a handler that captured one, may not flow into a `Task.spawn` closure that outlives the current scope (`V6002`).

## Timeouts, retries, and budgets

All three are ordinary std functions over thunks (design §5.9):

```vow
fn retry<T, e>(policy: Retry.Policy, action: fn() -> T ! e) -> T ! {Clock, Random | e}
fn timeout<T, e>(limit: Duration, action: fn() -> T ! e) -> T ! {Clock, Task, Fail<Timeout> | e}
fn with_budget<T, e>(b: Budget.Limits, action: fn() -> T ! {Budget | e}) -> T ! {Fail<BudgetExceeded> | e}
```

- `retry` starts a **new invocation** per attempt. It never resumes a failed one. `retry_on` in the policy is a pure predicate over the action's error union. When attempts run out, the last error propagates; no extra "exhausted" tag is added. The std HTTP client refuses to retry non-idempotent methods without an idempotency key.
- `timeout` cancels the action's task at its next effect operation, joins it, then fails with `Timeout`. Finalizers run.
- `Budget` is an effect with `reserve` and `settle`. `Llm` and `Http` handlers consume it when it is installed. Exceeding it fails with `BudgetExceeded`, whose `kind` is `Tokens`, `Usd`, `Calls`, `Bytes`, or `Time`. Child tasks inherit the budget, split atomically.

Together, from design §15.10:

```vow
import std/http

error Timeout
fn fetch_both(a: Url, b: Url) -> (String, String) ! {Http, Task, Clock, Random, Fail<HttpError | Timeout>} {
  let policy = Retry.Policy { retry_on: fn(e) { match e { RateLimited { .. } => true, _ => false } },
                              max_attempts: 3, backoff: Duration.millis(200), jitter: true, deadline: None }
  timeout(Duration.seconds(5), fn() {
    Task.scope(fn(s) {
      let fa = Task.spawn(s, fn() { retry(policy, fn() { Response.text(Http.get(a), 1_000_000).trust(@trust("display only")) }) })
      let fb = Task.spawn(s, fn() { retry(policy, fn() { Response.text(Http.get(b), 1_000_000).trust(@trust("display only")) }) })
      (Task.join(fa), Task.join(fb))
    })
  })
}
```

A budget is installed as a handler. From `main` in design §15.7:

```vow
with Llm.anthropic(key, Model.of("claude-sonnet-5-5")), Budget.limits(tokens: 20_000, usd: 0.50) {
  let t = extract_ticket(Untrusted.of("Login page 500s since 9am, blocking all customers"))
  Console.print("{t.priority}: {t.title}")
}
```

## Determinism

Evaluation is strict and left to right, arguments before the call. `Map` and `Set` iterate in insertion order on every backend. `Clock`, `Random`, and `Task` are effects, so a test can replace all three (design §8.7):

```vow
test "deterministic under virtual time" {
  with Http.scripted([(Any, Response.status(200, "x"))]), Clock.virtual(), Random.seeded(1), Task.deterministic(1) {
    expect_eq(fetch_both(Url.from("https://a"), Url.from("https://b")), ("x", "x"))
  }
}
```

Under `Task.deterministic(seed)` scheduling is reproducible. `Clock.virtual()` advances only when told to. This is how `with` doubles as Vow's deterministic-simulation mechanism. See [Testing](/docs/tour/testing).

## Runtime model

The first backend compiles to JavaScript with a CPS trampoline and is single-threaded. A live host handler, such as `Clock.sleep` or `Http.send`, suspends by returning a step the driver awaits (design §13.3). The native backend (M5) will run tasks on worker threads and promote values sent across threads to atomic reference counts.

## Not in v0

- An `Async` effect, `async`/`await`, or colored functions (design §5.6).
- Durable workflows. They are a later official package, not part of the language (design §1.1, §11.3).
- Actors. `spawn` and `actor` are reserved keywords.
- Shared mutable state or locks in user code.

## What the compiler checks

- Code that uses `Task` operations declares `Task` in its row (`V3001` otherwise).
- Child rows flow into the parent's row through the `e` variables of `Task`'s operations.
- A capability or capturing handler does not escape into a task that outlives its scope (`V6002`).
- A `Fiber<T>` does not outlive its scope.
