Types say what shape a value has. Refinements and contracts say what is true about it. Both are part of the signature, so both are what a reviewer reads.

## Refinement types

A refinement is a base type plus a predicate, written with `where`. Inside the predicate, `it` is the value.

```vow
type Age = Int where 0..=150
type Port = Int where 1..=65535
type Percent = Float where 0.0..=100.0
type Cents = Int where it >= 0
type Email = String where is_email(it)
type Password = String where it.len >= 12
type NonEmpty<T> = List<T> where it.len > 0
```

A range on its own is shorthand for "`it` is in this range". `a..b` excludes `b`, and `a..=b` includes it. Predicates must be pure functions, so checking one never performs an effect.

A refined value can be used wherever its base type is expected. An `Age` is an `Int`.

```vow
fn next_year(age: Age) -> Int {
  age + 1
}
```

## Where refinements are checked

A value only becomes refined in one of two ways, and never silently.

**At compile time**, when the value is known or provable:

```vow
let port: Port = 8080        // literal: checked by the compiler
let bad: Port = 70000        // compile error E0301
```

**At the boundary**, when an unrefined value is converted explicitly. Every refined type has a `from` constructor that may fail:

```vow
fn parse_age(s: String) -> Age ! {Fail<Invalid>} {
  Age.from(Int.parse(s))
}
```

`Age.from(n)` has type `Age ! {Fail<Invalid>}`. Values from the outside world use `.validate`, which is the same check applied to an [`Untrusted`](/docs/tour/capabilities) value:

```vow
let email = req.param("email").validate(Email)   // Email ! {Fail<Invalid>}
```

Once a value has type `Email`, nothing downstream re-checks it. Validation happens once, at the edge, and the type carries the proof.

## Refinements flow through code

The checker tracks facts from conditions, so many conversions need no runtime check:

```vow
fn to_age(n: Int) -> Option<Age> {
  if n >= 0 and n <= 150 { Some(n) } else { None }
}
```

Inside the `if` branch, `n` is known to satisfy `0..=150`, so `Some(n)` has type `Option<Age>` with no call to `Age.from`.

## Preconditions: requires

`requires` states what must be true of the arguments. It goes between the signature and the body.

```vow
fn divide(a: Int, b: Int) -> Int
  requires b != 0
{
  a / b
}
```

Every caller must satisfy the precondition. When the checker can see that it holds (a literal, a refined type, a dominating `if`), there is no runtime cost. When it cannot, the caller gets an error asking it to establish the fact, usually by checking first.

## Postconditions: ensures

`ensures` states what is true of the return value. `result` names it.

```vow
type Account = { id: Uuid, balance: Cents, frozen: Bool }
type WithdrawError = Insufficient | Frozen

fn withdraw(from: Account, amount: Cents) -> Account ! {Fail<WithdrawError>}
  requires amount > 0
  ensures result.balance == from.balance - amount
  ensures result.id == from.id
{
  if from.frozen { fail Frozen }
  if amount > from.balance { fail Insufficient }
  { from with balance: from.balance - amount }
}
```

Three things are worth noticing:

- `ensures` applies to normal returns. If the function fails, there is no `result` to check.
- `from.balance - amount` must be a `Cents`, so it must be non-negative. The checker knows `amount <= from.balance` after the second `if`, so it can prove this.
- There is no `old(from.balance)`. Arguments are immutable values, so `from` in the postcondition is exactly the value passed in.

## How each contract is discharged

The design is that each contract is handled in the strongest way available:

1. **Proven statically.** The checker hands simple arithmetic, comparisons, and facts from conditions to an SMT solver. A proven contract costs nothing at runtime.
2. **Checked at the boundary.** A contract the solver cannot prove becomes an assertion at the function's entry (for `requires`) or exit (for `ensures`).
3. **Tested.** Every contract that is not proven also becomes a generated property test that `vow test` runs. See [Testing](/docs/tour/testing).

`vow check --contracts` is planned to report which path each contract took:

```bash
$ vow check --contracts
src/bank.vow:5   withdraw  requires amount > 0                              proven at all 3 call sites
src/bank.vow:6   withdraw  ensures result.balance == from.balance - amount  proven
src/bank.vow:7   withdraw  ensures result.id == from.id                     proven
src/sort.vow:14  sort      ensures result.is_sorted()                       runtime check, property test
```

## Contracts on collections

Contracts can call pure functions, which keeps them readable:

```vow
fn sort(xs: List<Int>) -> List<Int>
  ensures result.len == xs.len
  ensures result.is_sorted()
{
  xs.sort()
}

fn top<T>(xs: NonEmpty<T>, score: (T) -> Int) -> T
  ensures xs.all(x => score(x) <= score(result))
{
  xs.max_by(score)
}
```

`top` takes a `NonEmpty<T>`, so it does not need an `Option` return type: the refinement already rules out the empty case.

## What the compiler checks

- Refinement predicates and contract expressions are pure and total.
- A refined type is never produced from an unrefined value without a proof, a `from`, or a `validate`.
- `requires` holds at every call site, by proof or by an explicit check.
- `ensures` holds at every normal return, by proof, by a runtime check, and by a generated property test.
- Contracts are part of the signature, so changing one is a `changes-signature` edit. See [Diagnostics](/docs/agents/diagnostics).
