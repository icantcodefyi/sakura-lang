Most supply-chain attacks and injection bugs rely on code doing more than it should: a dependency that reads files it was never meant to see, a string from a request that reaches a SQL query, a token that ends up in a log. Sakura Lang's design makes each of these either impossible or a visible, reviewable decision.

## Effects are requirements, handlers are authority

`Fs` in a signature says "this function may perform filesystem operations". It does not say which files. The **installed handler** decides that ([design §6.1](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)).

A handler for `Fs` is built from a `Dir` capability value. Every path is resolved relative to that directory, and symlink escapes are rejected. Authority lives in capability values that handlers close over, not in effect labels.

The effect row still matters: a function can only perform the effects in its row, and a pure function cannot touch the outside world at all. But the row is what a function *needs*. What it may actually *reach* is set by whoever installs the handler.

## Root authority comes from the host

The entry point is `pub fn main() -> Unit ! {…}`. The host supplies root handlers for exactly the std effects `main` declares, and nothing else. Only std effects may appear in `main`'s row (`V6010`), because only they have host root handlers.

Root handlers are limited by the `[permissions]` table in the project manifest:

```toml title="sakura.toml"
[permissions]
fs.read  = ["./data", "./templates"]
fs.write = ["./data/out"]
net      = ["api.anthropic.com:443", "localhost:5432"]
env      = ["DATABASE_URL", "ANTHROPIC_API_KEY"]
process  = []          # no subprocesses
```

`sakura run` passes this table as JSON in `SAKURA_PERMISSIONS`; the host filesystem, HTTP/serving and environment adapters enforce it. Running emitted JS directly without that variable does not establish this ceiling. Trusted FFI is outside this language-level boundary. There is no separate `Net` effect: the `net` list limits the network effects `Http` and `Serve` (`Sql.postgres` is not implemented), and `env` limits which variables `Env` can read. A `main` that declares an effect whose permission list is empty, such as `Http` with an empty `net` list, fails at **startup**, not at first use, and exits with status `75` (permission denied).

## Narrowing authority

`Dir` and `File` have no public constructors. `Fs.root()` supplies a directory capability, and `Dir.subdir` narrows it. `Http.scoped(hosts: List<String>)` and `Env.only(keys)` attenuate outer handlers by data; `NetScope`, `EnvScope`, and `SecretStore` are not current APIs.

Attenuating handlers are ordinary std functions: `Fs.rooted(dir)`, `Http.scoped(hosts)`, and `Env.only(keys)`.

This CLI tool narrows the root filesystem to `data/` before reading anything ([design §15.6](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)):

```sakura title="src/main.sakura"
import std/cli.{Cli, CliError}
import std/fs.{Fs, FsError, Dir}
import std/path.{Path}

type Args = { input: Path, top: Int }   // `sakura run -- --input notes.txt --top 5`

fn word_counts(text: String) -> Map<String, Int> {
  List.fold(String.split(String.to_lower(text), " "), Map.empty(), fn(acc, w) {
    if w == "" { acc } else { Map.update(acc, w, fn(n) { Option.unwrap_or(n, 0) + 1 }) }
  })
}

pub fn main() -> Unit ! {Console, Cli, Fs, Fail<CliError | FsError>} {
  let args: Args = Cli.parse(Cli.args())
  // Narrow the root Fs handler to the data directory before touching files.
  with Fs.rooted(Dir.subdir(Fs.root(), "data")) {
    let text = Fs.read_text(args.input).trust(@trust("word counting cannot be influenced by content"))
    let top = List.slice(List.sort_by(Map.entries(word_counts(text)), fn(e) { 0 - e.1 }), 0, args.top)
    for (word, n) in top { Console.print("{word}: {n}") }
  }
}
```

`Cli` is an effect: `Cli.args()` reads the command line through the root handler, and `Cli.parse` turns the arguments into the record type named by the annotation on `args`. Inside the `with` block, every `Fs` operation, including those performed by functions it calls, resolves against `data/`.

## Scoped escape rules (M3 completion)

A capability, or a handler that captured one, is a **scoped value** ([design §6.3](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)). It may be passed down the call stack, stored in records that are themselves scoped, and returned from functions. It may not flow into:

- a `Task.spawn` closure whose `Scope` outlives the `with` that produced the value (there are no detached tasks in v0),
- a top-level `let`,
- a value returned from the `with` body that introduced the scope.

A violation is `V6002`. Resources such as files and connections follow the same rule: the result of `Fs.with_file(path, mode, fn(file) { … })` may not contain `file` (`V6003`).

## Dependency authority (design; package tooling planned)

A package's effects are computed from its code, not hand-written. `sakura deps capabilities` prints the authority graph of your dependencies ([design §6.5](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)).

There is no ambient authority and no `import` that grants anything. You grant a dependency authority by installing a handler around the calls you make to it. In this sketch, `acme/thumbnails` is a hypothetical package whose `render` declares `! {Fs, Fail<FsError>}`:

```sakura
import std/fs.{Fs, FsError, Dir}
import std/path.{Path}
import acme/thumbnails

fn make_thumbnail(name: Path) -> Unit ! {Fs, Fail<FsError>} {
  // The dependency sees only the uploads directory, whatever it tries to open.
  with Fs.rooted(Dir.subdir(Fs.root(), "uploads")) {
    thumbnails.render(name)
  }
}
```

If an update adds `Http` to `render`'s row, `make_thumbnail` no longer type checks until you decide whether to allow it. Packages cannot run code at install time: there are no build scripts in v0. A package that uses `@external` FFI bindings is marked `trusted` in the build manifest.

## Untrusted data

`of`, `check`, `trust`, and `len` work today. Refined-target `validate` below is planned M3 completion work.

`Untrusted<T>` wraps data from outside the deployment: raw request bodies, file contents read as text (`Fs.read_text`), response text (`Response.text`), and free-text LLM output (`Llm.generate_text`). Environment variables are not in that list: they are set by the operator and gated by the manifest's `env` list, so `Env.get(key)` returns a plain `Option<String>`. `Untrusted<T>` supports:

| Operation                        | Result                                                            |
| -------------------------------- | ----------------------------------------------------------------- |
| `.validate()`                    | `Result<V, Violation>` for any refined type `V`, named by annotation: `let e: Email = Untrusted.validate(u)?`. |
| `.check(clause, pred)`                   | `Result<T, Violation>`.                                           |
| `.len()`                         | The length, without trusting the content.                         |
| `.trust(@trust("reason"))`       | `T`. An explicit, greppable escape hatch.                         |
| `Untrusted.of(t)`                | Wraps a value, for tests.                                         |

Validating against a refinement is the normal path:

```sakura
type Email = String where String.len(it) <= 254 && String.contains(it, "@")
error InvalidEmail

fn read_email(raw: Untrusted<String>) -> Email ! {Fail<InvalidEmail>} {
  match raw.validate() {      // V = Email, inferred from the return type
    Ok(email) => email,
    Err(_) => fail InvalidEmail,
  }
}
```

`Untrusted<T>` is `Show`, so it can be logged. Schema-decoded values (`Request.json`, `Json.decode`, `Llm.generate`) are already validated against the target type's refinements and come back as `T`, not `Untrusted<T>`.

## Tagged templates never splice

`sql"…"`, `html"…"`, `url"…"`, and `shell"…"` are tagged templates ([design §4.11](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)). A tagged string desugars to a call to the tag module's `template` function, with the literal parts and the interpolated values passed separately:

```text
sql"select * from users where email = {email}"
  ==> sql.template(["select * from users where email = ", ""], [SqlValue.from(email)])
```

Interpolated values are **never spliced raw**. Each one is type checked against the tag's parameter type. For `sql` that is `SqlValue`, which becomes a bound parameter. `html` escapes text by construction. So untrusted input is safe in a template:

```sakura
import std/sql.{Sql, SqlError}

type Post = { id: Int, title: String }

fn search(q: Untrusted<String>) -> List<Post> ! {Sql, Fail<SqlError>} {
  Sql.query(sql"select id, title from posts where title = {q}")
}
```

`q` reaches the database as a parameter value, never as SQL text. Raw-text APIs such as `Html.raw`, which takes a `TrustedHtml`, do not accept `Untrusted<T>`.

This holds because the template's result types are `pub opaque type`s. `Query<R>` and `Html` are exported by name only: other modules can pass them around, but constructing one outside its declaring module is `V1006`, so the template is the only way to build a query and escaping code the only way to build HTML.

## Secrets

`Secret<T>` wraps credentials. `Env.secret("KEY")` returns `Option<Secret<String>>`. A secret is not `Show`, `Eq`, `Ord`, or `Schema`, so it cannot be interpolated, logged, snapshotted, or serialized. Interpolating one is `V2031`. Only std sinks accept it, such as `Http.bearer`:

```sakura
import std/http.{Http}
import std/request.{Request}
import std/response.{HttpError}
import std/log.{Level}
import std/url.{Url}
import std/decimal.{Decimal}

pub fn call_billing(amount: Decimal) -> Unit ! {Env, Http, Log, Fail<HttpError>} {
  let token = Env.secret("BILLING_TOKEN").expect("BILLING_TOKEN")
  let req = Http.bearer(Request.post_json(Url.from("https://billing/charge"), amount), token)
  Log.event(Level.Info, "charging {amount}", [])          // ok: Decimal is Show
  // Log.event(Level.Info, "token {token}", [])            // V2031: Secret<String> is not Show
  let _ = Http.send(req)
}
```

Adapters that genuinely need the raw value use `Secret.expose(s, @trust("reason"))`. The planned `sakura audit` will list every use with its reason. This prevents accidental disclosure, not deliberate leakage.

## The trusted computing base

Some things are assumed, and Sakura Lang says so. The trusted computing base is the compiler, the runtime, the std root handlers, FFI bindings marked `@external`, every `@trust` site, the host platform, and later the SMT solver ([design §6.6](https://github.com/icantcodefyi/sakura-lang/blob/master/docs/design.md)). The planned `sakura build --manifest` will write this list with content hashes. Each item has the `trusted` status in the [guarantee model](/docs/tour/contracts#the-guarantee-model).

Compiler fixes never widen authority silently. A fix that would change authority carries `impact: authority_change` and is never applied by `sakura fix` automatically. See [Diagnostics](/docs/agents/diagnostics).

## What the compiler checks

- A function performs only the effects in its row. Every performed operation has an installed handler.
- `main` declares only std effects (`V6010`). Root handlers are limited by `[permissions]`; a denied permission stops the program at startup (exit `75`).
- Prelude `Trust` is compiler-known. `@trust("reason")` is accepted only directly in a trusted sink argument; other uses report `V6001`.
- Full scoped capability/resource escape checks (`V6002`/`V6003`) are M3 completion gates, not a completed security guarantee.
- `Secret<T>` is never shown, logged, snapshotted, or serialized (`V2031`).
- Tagged templates receive interpolations as values, never raw text.

## Not in v0

- **Information-flow control.** `Secret<T>` stops accidents, not a determined leak (design §1.1).
- **Declared capability ceilings for packages.** The design calls for computed package authority; package tooling is not implemented. Mandatory ceilings in `sakura.toml` for published packages are planned for v1 (design §16).
