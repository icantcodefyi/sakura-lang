## Install in one command

First install [Node 26](https://nodejs.org). `sakura run` and `sakura test` need it to run
your program. Then:

```bash title="npm (macOS, Linux, Windows)"
npm install --global sakuralang@beta
sakura --version
```

```bash title="Homebrew (macOS, Linux x64)"
brew tap icantcodefyi/sakuralang
brew trust --tap icantcodefyi/sakuralang
brew install sakuralang-beta
sakura --version
```

```text
sakura 1.0.0-beta.4 (40af20ce096074012bbd2344129da441589d3e6c)
```

That's it. Go to the [Quickstart](/docs/quickstart) to run your first program.

Good to know:

- The compiler alone can check and build code without Node. Only running and testing need it.
- Neither the installer nor npm installs Node for you.
- Homebrew installs Node as a dependency. It installs the formula's current version, not a
  pinned one, so check the printed version before you report a problem.

## The beta

`v1.0.0-beta.4` is a beta of 1.0. **It is not for production**: it may have bugs and may change
before 1.0.0. Every breaking change until then is listed in the [changelog](/changelog) with a
migration ([Stability](/docs/stability)). It is a
[GitHub prerelease](https://github.com/icantcodefyi/sakuralang/releases/tag/v1.0.0-beta.4).

The beta is not on the default channels. Until `v1.0.0`, `npm install --global sakuralang` (the
`latest` tag) and `brew install sakuralang` install `0.1.0`, the earlier preview. These docs
track `main`; see [changes since 0.1.0](/docs/changes).

The two Homebrew formulas both install `sakura`. Remove one (`brew uninstall sakuralang`)
before you install the other.

To install `0.1.0` with npm instead, run `npm install --global sakuralang@0.1.0`.

## Release installer

Use this on macOS or Linux if you would rather not use npm or Homebrew. Download the script,
read it, then run it:

```bash title="Release installer"
version=0.1.0
curl -fsSL "https://github.com/icantcodefyi/sakuralang/releases/download/v${version}/install.sh" -o install.sh
less install.sh
sh install.sh --version "$version"
export PATH="$HOME/.local/bin:$PATH"
sakura --version
```

For the beta, set `version=1.0.0-beta.4`.

The installer:

- picks the build for your CPU and system;
- checks the download against `SHA256SUMS`, and also checks its attestation if the GitHub CLI
  (`gh`) is installed (without `gh` it reports `integrity verified, not attested`);
- installs to `~/.local/bin`, or to `--prefix /absolute/path`.

To keep `sakura` available in new shells, add the `PATH` line to your shell profile yourself.

macOS binaries from v0.1.0 on are signed with a Developer ID (team `P62B65A837`) and notarized
by Apple. `0.1.0-alpha.1` was not signed.

## Windows x64

Use npm (above), or the PowerShell installer. Download it, read it, then run it:

```powershell title="install.ps1"
Invoke-WebRequest "https://github.com/icantcodefyi/sakuralang/releases/download/v0.1.0/install.ps1" -OutFile install.ps1
Get-Content install.ps1
./install.ps1 -Version 0.1.0
```

For the beta, take `install.ps1` from that release and pass `-Version 1.0.0-beta.4`.

It checks the ZIP against `SHA256SUMS` and installs `sakura.exe` to
`%LOCALAPPDATA%\Programs\sakuralang\bin`. Add that folder to `PATH` yourself. Use Windows 10
x64 or later; the MSVC runtime is statically linked, so you do not need the Visual C++ runtime. Windows on ARM is not supported, and proof caching is not implemented on
Windows.

## Platforms

| System | CPU | npm | Homebrew | Installer | Oldest system |
| --- | --- | --- | --- | --- | --- |
| macOS | Apple silicon | yes | yes | yes | macOS 12.0 |
| macOS | Intel | yes | yes | yes | macOS 12.0 |
| Linux (glibc) | x64 | yes | yes | yes | glibc 2.35 (Ubuntu 22.04) |
| Linux (glibc) | ARM64 | yes | no | yes | glibc 2.35 (Ubuntu 22.04) |
| Windows | x64 | yes | no | `install.ps1` | Windows 10 |

There is no release build for Alpine (musl), 32-bit ARM (`armv7`) or Windows on ARM.

"Oldest system" is what the binary is built to need. The automated tests run on newer
systems.

### Platform claims

Each claim is tied to a named release:

- **Supported.** CI tests the target, and a fresh install from the public channels passes the
  whole acceptance list on a hosted runner of that system and CPU. An install or run failure
  there is a release bug, fixed in a new version.
- **Expected to work.** The same binary on a system without a hosted runner. The project has
  not run it on that device.
- **Community-confirmed.** An expected-to-work setup that a user ran through the whole
  acceptance list, recorded as `confirmed on <device>, <OS build>, <version> (#issue)`.

For v0.1.0, every platform in the table is **Supported**. The published-install check
([run 39375162895](https://github.com/icantcodefyi/sakuralang/actions/runs/39375162895),
2026-10-20) installed `0.1.0` from the public channels on fresh GitHub-hosted runners and
passed on all six rows:

| Target | Runner | Channels |
|---|---|---|
| `aarch64-apple-darwin` | `macos-15` | npm, Homebrew, installer |
| `x86_64-apple-darwin` | `macos-15-intel` | npm, Homebrew, installer |
| `x86_64-unknown-linux-gnu` | `ubuntu-22.04` | npm, Homebrew, installer |
| `aarch64-unknown-linux-gnu` | `ubuntu-22.04-arm` | npm, installer |
| `aarch64-unknown-linux-gnu` | Debian bookworm container on `ubuntu-24.04-arm`, 1,800 MB memory limit | npm, installer |
| `x86_64-pc-windows-msvc` | `windows-2025` | npm, installer |

These claims are for v0.1.0. A later release earns them again with its own run. A Windows
Server runner does not prove a Windows 11 device, and a Rosetta run of the archive alone
cannot confirm Intel npm or Homebrew installs.

### Raspberry Pi 4 and 5

**Expected to work** with the v0.1.0 Linux ARM64 release, on 64-bit Raspberry Pi OS. The
project has not run it on Pi hardware.

A Debian bookworm arm64 container with a 1,800 MB memory limit, standing in for a 2 GB Pi 4,
passed the whole acceptance list
([run 39375162895](https://github.com/icantcodefyi/sakuralang/actions/runs/39375162895)).
Peak memory was not measured, and a container is not a Pi.

Use a 64-bit OS: `uname -m` should print `aarch64`. Node's ARM64 build needs `libatomic1`.
Raspberry Pi OS ships it; on a minimal Debian image run `sudo apt install libatomic1` first.

To install Node 26 with [nvm](https://github.com/nvm-sh/nvm#installing-and-updating) in Bash,
download and read its installer, then run it:

```bash
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh -o install-nvm.sh
less install-nvm.sh
bash install-nvm.sh
export NVM_DIR="$HOME/.nvm"
. "$NVM_DIR/nvm.sh"
nvm install 26
nvm use 26
node --version
npm --version
```

Check that Node prints `v26.x.x`, then install with npm as your normal user.

## Native builds (experimental)

`sakura build --target native` compiles a program to an executable,
`target/sakura/native/main`. The executable needs no Node and no Sakura Lang install to run.
This is **experimental**: the flag may change or go away in a later release without a
migration. See [Native](/docs/native).

Which binaries can do it:

- The macOS Apple silicon, Linux x64 and Linux arm64 release binaries, from v1.0.0-beta.4.
  Every channel (installer, npm and Homebrew) installs the driver it needs,
  `lib/sakura/native/libsakura_native_driver.a`, next to `bin/`. Set `SAKURA_NATIVE_LIB_DIR`
  to use another directory.
- On Intel macOS and Windows x64, a compiler built from source with
  `cargo build --release -p sakura_cli --features native` (the executable is `main.exe` on
  Windows). Windows executables carry no debugger symbols; defect traces still name Sakura
  source positions.
- Other release binaries refuse `--target native` with exit code 2.

A native build needs a system linker. Sakura Lang does not bundle one:

- **macOS:** the Xcode Command Line Tools (`xcode-select --install`).
- **Linux:** a C compiler on `PATH` as `cc`, for example `sudo apt install gcc` (Debian,
  Ubuntu) or `sudo dnf install gcc` (Fedora).
- **Windows (source builds):** MSVC's `link.exe`, from the Visual Studio Build Tools with the
  "Desktop development with C++" workload. `sakura` finds it in the Visual Studio
  installation, not on `PATH`.

Without a linker, the build stops with [`V8007`](/docs/errors/V8007).

## Report your platform

Start with `sakura --version` and [create a project](/docs/quickstart#2-create-a-project). To
record a **Community-confirmed** platform,
[file a platform report](https://github.com/icantcodefyi/sakuralang/issues/new) with:

- the device, OS build, exact Sakura Lang version and commit, and `node --version`;
- `uname -a` (or `winver`), and `/etc/os-release` on Linux;
- the result of the whole acceptance list: `new cli`, `check`, `test`, `build`, `run`,
  `run --target wasm`, an MCP initialize handshake, `setup --apply` twice, and the expected
  refusal to run when Node is absent.

A successful install alone is not a confirmation. No device confirmations are recorded yet.

Benchmark results in `bench/` apply only to the project's reference machine. A platform claim
says nothing about speed on a Pi or any other machine.

Details for contributors: the
[target inventory](https://github.com/icantcodefyi/sakuralang/blob/main/packaging/targets.json)
and the
[platform plan](https://github.com/icantcodefyi/sakuralang/blob/main/docs/plans/road-to-1.0.md#6-platforms-b-and-c-design-17180-acceptance-17227).
