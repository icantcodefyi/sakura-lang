## Native code against C, Rust, Go, OCaml and Koka

[`sakura build --target native`](/docs/native) turns a program into a machine-code executable.
Here it runs the same 22 programs as hand-written C, Rust, Go, OCaml and Koka, with the same
algorithm in the same order and every program's answer checked. Each number is the **work** a
program does for one call: the CPU instructions it runs, counted on one machine.
[How we measure](#how-we-measure) has the details.

Native Sakura is young, and on most programs it is far behind. It is closest on recursion, trees
and maps, and furthest on loops over lists and arrays, on effect handlers and on text. The
reasons are [below](#why-native-sakura-is-fast-and-what-still-holds-it-back).

### Why native Sakura is fast, and what still holds it back

- **Cranelift machine code.** The native backend compiles straight to machine code with
  Cranelift, the code generator Wasmtime uses. There is no interpreter or JIT warm-up.
- **Memory reused in place.** Sakura counts references for you. When nothing else holds a value,
  an update rewrites it where it is (Perceus reuse), so a loop that rebuilds a list or tree can
  allocate nothing.
- **Borrowing instead of copying.** A function that only reads its argument borrows it, and the
  call does no reference-counting work.
- **Unboxed arithmetic in typed code.** An `Int` or `Float` in a typed local or a handler's
  state is a plain machine number; `nbody`'s inner loop allocates no boxes at all. A number inside
  a `List` or generic code is still a boxed word.
- **No garbage-collector pauses.** Memory is freed the moment its last reference goes, so there is
  no collector to stop the program.
- **What holds it back today.** A `List` is a persistent tree, so `sieve`, `spectral_norm` and
  `nbody` read and write through it where C indexes an array. Every effect operation pays for
  a handler dispatch, where the C, Rust and Go versions make a plain function call (the `handled`
  programs). `deltablue`'s persistent maps copy
  where the other languages mutate. And in these numbers the runtime re-checks a string's UTF-8
  on every text call, so `tokenizer` and `json_validate` grow faster than their input. That is
  fixed on `main` since they were counted: `tokenizer` at 100,000 drops from about 595 billion
  to about 1 billion instructions per call, and the next release's baseline will show it.

### Why the JavaScript build is fast

- **Compiled ahead of time.** `sakura build` turns your program into plain JavaScript or
  WebAssembly. With [`--target native`](/docs/native) (experimental) it builds an executable
  using Cranelift. Types are checked once, at compile time, and nothing of them is left in the
  output.
- **Effects become plain calls.** A handled effect, such as the counter in the `handled`
  programs, compiles to a direct function call.
- **Memory is reused in place.** On WebAssembly and native code, the compiler adds the reference
  counting for you, so there is no garbage collector. When nothing else holds a value, an update
  rewrites it where it is and allocates nothing. This technique is called Perceus reuse;
  [Memory](/docs/tour/memory) explains it.
- **Reading borrows; it doesn't copy.** A function that only reads its argument borrows it, so
  the call does no reference-counting work (WebAssembly and native).
- **Lists are built in place.** `List.map`, `List.filter` and their siblings fill a private buffer
  and hand back the finished list, so they never copy while they grow it.
- **No hidden copies.** Values never change behind your back, so sharing one costs nothing. When
  an update must copy because the old value is still used, `sakura check` tells you with warning
  [`W8001`](/docs/errors/W8001) and points at the use that forces the copy.
- **Proved checks are left out.** A `requires` or `ensures` check runs while the program runs,
  unless [`sakura verify`](/docs/agents/verify) proved it always holds. Then the build leaves it
  out.
- **A checker built for the loop.** The compiler is written in Rust and caches its analysis of
  the standard library, so a check of a small file starts mostly done.

## How we measure

<details>
<summary>Instruction counts, the reference machine and blessed baselines</summary>

### The run

<BenchRun />

Every number above is read when the site is built, from the **blessed** baseline in
[`bench/baselines`](https://github.com/icantcodefyi/sakuralang/tree/main/bench/baselines) and the
result files of the same commit in
[`bench/results`](https://github.com/icantcodefyi/sakuralang/tree/main/bench/results). A baseline
is blessed when a full counted run at a release's preparation commit is accepted. From then on,
every change is compared with it. The numbers are specific to these programs and this
one machine. They are not a ranking of languages.

### Instruction counts

The measure is **instructions retired per call**: how many CPU instructions finish for one call
of the program, read from macOS's `/usr/bin/time -l` on the reference Mac. As with
[rustc-perf](https://perf.rust-lang.org), the reason is that a count barely moves when other
programs share the machine. So the suite can run while other work goes on.

<CountFlow />

Each cell is one program at one input size on one engine. The harness picks a call count `k`,
then runs five pairs of fresh processes. One process of a pair calls `run(n)` once, the other
`1 + k` times. Start-up, loading and the first call's compilation are in both, so their
difference divided by `k` is the cost of one warm call. The cell is the median of the five pairs.
Every program has an oracle: a cell counts only after the program returns the recorded checksum
for every input.

Node runs with `--predictable --min-semi-space-size=16 --max-semi-space-size=16`.
`--predictable` keeps V8's garbage collector and compiler on the main thread, so a count does not
depend on how threads were scheduled. The fixed young generation keeps it from depending on where
the program's files sit on disk.

An instruction count is not a time. It does not see cache misses, branch mispredictions, or how
many instructions a core finishes per cycle, and two engines can run the same instructions at
different speeds. Every ratio on this page is a ratio of counts.

### What "advisory" means

A reading is **advisory** when it is reported but blocks nothing. Two kinds are:

- **Bun rows.** Bun's counts vary more than Node's (see [Spread](#spread)). So a Bun row is
  flagged when it moves more than 10%, and it never blocks a change.
- **Wall times on a busy machine.** The goals against other languages are set in time, so they
  are read on the wall time of the same runs. The machine was busy while those ran, so the times
  show the direction only.

The instruction counts themselves are not advisory: they are the baseline every change is
compared with.

### Spread

A cell's spread is (max − min) / median over its five pairs. One outlying pair widens the spread
but barely moves the median, so the last column counts the cells whose middle three pairs also
differ by more than 1%.

### Reproduce

On a Mac with the toolchains pinned in
[`bench/toolchains.toml`](https://github.com/icantcodefyi/sakuralang/blob/main/bench/toolchains.toml),
at the commit above:

```sh
bench/bench run --suite js --instructions --json js.json
bench/bench run --suite wasm --instructions --json wasm.json
bench/bench run --suite native --lane matched --instructions --json native.json
bench/bench compile --instructions --json compile.json
bench/bench envelope wasm.json native.json --json envelope.json --md envelope.md
```

Counts from another machine are not comparable with these: a different CPU, OS or engine build
runs different instructions. The baseline files hold every size, every raw count and the wall
time beside it. The procedure that turns a run into a baseline is in
[`docs/release.md`](https://github.com/icantcodefyi/sakuralang/blob/main/docs/release.md#2-instruction-count-baseline-and-bless).
