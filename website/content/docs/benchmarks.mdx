`3bf2343f` is a commit on main after `v0.1.0`. It carries JavaScript-backend work that is not
in the `0.1.0` packages ([changes on main](/docs/changes#faster-on-main)): owned updates of
fresh lists and flat `List<Bool>` (`nbody`, `sieve`) and the `Int`-key path of `Map`
(`map_set`). It also fixes the size of V8's young generation on every measured Node process,
which changes every Node count once. The counts for the released `v0.1.0` are those of the
earlier baseline at `320c9980`, kept in
[`bench/baselines/archive/320c9980/`](https://github.com/icantcodefyi/sakuralang/tree/main/bench/baselines/archive/320c9980);
a counted check of the `v0.1.0` candidate on `fib` and `shapes` passed against it.

The [benchmark suite](https://github.com/icantcodefyi/sakuralang/tree/main/bench) runs the
same workloads written in Sakura Lang and by hand in JavaScript, Rust, Go, OCaml and Koka.
Every program has an oracle: a cell is measured only after it returns the recorded checksum
for every input. The numbers are specific to these workloads and this one machine. They are
not a language ranking.

## What is measured

The primary metric is **instructions retired per call**, read from macOS's
`/usr/bin/time -l`. As with [rustc-perf](https://perf.rust-lang.org), the reason is
repeatability: the count barely moves when other programs share the machine, so the suite runs
while other work goes on and needs no idle night ([design §17.264](https://github.com/icantcodefyi/sakuralang/blob/main/docs/design.md)).

<CountFlow />

Each cell is one program at one input size `n` on one engine. The harness calibrates a call
count `k`, then runs five pairs of fresh processes: one calls `run(n)` once, the other `1 + k`
times. Start-up, module loading and the first call's compilation are in both, so the
difference over `k` is the cost of a warm call. The cell is the median of the five pairs, and
its spread is (max − min) / median.

An instruction count is not a time. It does not see cache misses, branch mispredictions or how
many instructions a core retires per cycle, and two engines can retire the same instructions
at different speeds: in the first counted runs one Wasmtime cell's ratio of counts and its
ratio of times differed by half. A ratio below is a ratio of counts, never of times.

## Results

Every value is instructions retired per call (or per process, for the compiler) on the
reference Mac, at each program's largest size. A ratio is Sakura's count over hand
JavaScript's on the engine named. `K`, `M` and `G` are thousands, millions and billions. Node
runs with `--predictable --min-semi-space-size=16 --max-semi-space-size=16`: V8's garbage
collector and compiler stay on the main thread, and the young generation has a fixed size, so
that a count depends neither on scheduling nor on where the program's files sit on disk
(design §17.282).

## Against the targets

Design §17.109 set a ceiling per program on the ratio of Sakura to hand-written JavaScript on
the same engine, and asked for a median of at most 1.5 over the fifteen programs. Those are
same-engine ratios, so a ratio of counts can be read against them
([design §17.265](https://github.com/icantcodefyi/sakuralang/blob/main/docs/design.md)). At
the largest size, seven of the fifteen meet their ceiling on Node and five on Bun; the median
is 2.52 on Node and 2.48 on Bun.

Read plainly: on the JavaScript backend, most of the suite runs within 3× of hand-written
JavaScript (twelve programs under 1.5×, eight from 1.5× to 3.04×), and five programs are
4.4–6.5× behind: `nbody`, `deltablue`, `handled_fwd`, `map_set:int` and `spectral_norm`.
Where Sakura is ahead (`pipeline` 0.29×, `tokenizer` 0.35×, `handled` 0.88× on Node) the
cause is a specific mechanism, fusion of the pipeline, ownership of the consumed string, or a
handler compiled to a direct call, and it says nothing about other programs. The WebAssembly
backend is first-release code: 1.9–123× behind hand JavaScript by count on this suite, far
from native, with its worst cells on contracts, handlers and scalar loops. The native backend
is experimental, left out of release binaries, and not measured here.

Design §17.109 also set an envelope against Rust, Go, OCaml and Koka. Those ceilings were
set on wall time, and a count across different engines is not a time, so the envelope is
reported as information and not as a release gate (design §17.265). It is not met, and Sakura
Lang makes no cross-language speed claim. The native backend, experimental today, is where
that comparison will be made again.

What comes next, each landing with a counted before and after against this baseline: the
elements of a list updated in place (`nbody`); what remains in `deltablue`, `shapes` and
`rbtree`; forwarding handlers resolved when they are installed (`handled_fwd`); a sweep of
every ceiling; and, beside them, the WebAssembly cliffs (design §17.285).

### Since the baseline

- **Cold-path raising.** A defect on a path that is never taken (an `Int` overflow, an
  `expect` on a missing element) is thrown where it is detected. It is on main after
  `3bf2343f` and not released. Counted against the earlier `320c9980` baseline, before the
  fixed young generation, `spectral_norm` dropped 26% on Node (4.49× → 3.31× hand-written
  JavaScript); it has not been re-counted against this baseline.

## Spread

The spread is (max − min) / median over a cell's five pairs.

| Engine | Cells | Median spread | Cells over 1% |
|---|---:|---:|---:|
| Node, JavaScript backend | 198 | 0.35% | 15 |
| Node, WebAssembly backend and its hand JS | 198 | 0.29% | 13 |
| Wasmtime | 95 | 0.16% | 1 |
| Bun | 198 | 1.56% | 121 |

On Node and Wasmtime, in every cell over 1% the middle three pairs agree within 1%, so the
median holds. Bun is noisier: 48 of its cells spread over 1% even in their middle three. Read a
Bun count with its spread; a Bun row is advisory in a counted compare (design §17.265).

## Reproduce

On a Mac with the toolchains pinned in
[`bench/toolchains.toml`](https://github.com/icantcodefyi/sakuralang/blob/main/bench/toolchains.toml):

```sh
git checkout 3bf2343f
bench/bench run --suite js --instructions --json js.json
bench/bench run --suite wasm --instructions --json wasm.json
```

Counts from another machine are not comparable with these: a different CPU, OS or engine
build retires different instructions. The baseline files hold every size, every raw count and
the wall time beside it; the tables for every size are in
[`bench/results`](https://github.com/icantcodefyi/sakuralang/tree/main/bench/results)
(`2026-10-20-3bf2343f-*`), and the native and compiler runs are there as
`2026-10-19-320c9980-*`. The procedure that turns a run into a baseline is
[`docs/release.md` §2](https://github.com/icantcodefyi/sakuralang/blob/main/docs/release.md#2-instruction-count-baseline-and-bless).
