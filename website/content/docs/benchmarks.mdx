The [benchmark suite](https://github.com/icantcodefyi/sakuralang/tree/main/bench) runs the
same workloads written in Sakura Lang and by hand in JavaScript, Rust, Go, OCaml and Koka.
Every program has an oracle: a cell is measured only after it returns the recorded checksum
for every input. The numbers are specific to these workloads and this one machine. They are
not a language ranking.

## What is measured

The primary metric is **instructions retired per call**, read from macOS's
`/usr/bin/time -l`. As with [rustc-perf](https://perf.rust-lang.org), the reason is
repeatability: the count barely moves when other programs share the machine, so the suite runs
while other work goes on and needs no idle night ([design §17.264](https://github.com/icantcodefyi/sakuralang/blob/main/docs/design.md)).

<CountFlow />

Each cell is one program at one input size `n` on one engine. The harness calibrates a call
count `k`, then runs five pairs of fresh processes: one calls `run(n)` once, the other `1 + k`
times. Start-up, module loading and the first call's compilation are in both, so the
difference over `k` is the cost of a warm call. The cell is the median of the five pairs, and
its spread is (max − min) / median.

An instruction count is not a time. It does not see cache misses, branch mispredictions or how
many instructions a core retires per cycle, and two engines can retire the same instructions
at different speeds: in the first counted runs one Wasmtime cell's ratio of counts and its
ratio of times differed by half. A ratio below is a ratio of counts, never of times.

## Results

Every value is instructions retired per call (or per process, for the compiler) on the
reference Mac at commit `320c9980`, at each program's largest size. A ratio is Sakura's count
over hand JavaScript's on the engine named. `K`, `M` and `G` are thousands, millions and
billions. Node runs with V8's `--predictable` flag, which keeps its garbage collector and
compiler on the main thread so that their counts do not depend on scheduling.

## Spread

The spread is (max − min) / median over a cell's five pairs.

| Engine | Cells | Median spread | Cells over 1% |
|---|---:|---:|---:|
| Node, JavaScript backend | 198 | 0.14% | 4 |
| Node, WebAssembly backend and its hand JS | 198 | 0.30% | 12 |
| Wasmtime | 95 | 0.11% | 1 |
| Native (Rust, Go, OCaml, Koka) | 282 | 0.09% | 26 |
| Bun | 198 | 1.35% | 116 |
| Compiler processes | 6 | 0.28% | 1 |

On Node and Wasmtime every cell over 1% is one pair out of five; the middle three agree within
1%, so the median holds. Most native cells over 1% are Go, whose garbage collector runs
concurrently. Bun is noisier: 48 of its cells spread over 1% even in their middle three, and
JavaScriptCore's concurrency switches did not narrow them. Read a Bun count with its spread.

## Reproduce

On a Mac with the toolchains pinned in
[`bench/toolchains.toml`](https://github.com/icantcodefyi/sakuralang/blob/main/bench/toolchains.toml):

```sh
git checkout 320c9980
bench/bench run --suite js --instructions --json js.json
bench/bench run --suite wasm --instructions --json wasm.json
bench/bench run --suite native --lane matched --instructions --json native.json
bench/bench compile --instructions --json compile.json
```

Counts from another machine are not comparable with these: a different CPU, OS or engine
build retires different instructions. The full result files, with every size, every raw
count and the wall time beside it, are in
[`bench/results`](https://github.com/icantcodefyi/sakuralang/tree/main/bench/results)
(`2026-10-19-320c9980-*`). The procedure that turns a run into a baseline is
[`docs/release.md` §2](https://github.com/icantcodefyi/sakuralang/blob/main/docs/release.md#2-instruction-count-baseline-and-bless).
