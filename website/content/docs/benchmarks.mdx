## Sakura against hand-written JavaScript

The [benchmark suite](https://github.com/icantcodefyi/sakuralang/tree/main/bench) runs each
workload written in Sakura Lang and written by hand in JavaScript, the same algorithm in the same
order, and compares the two on one engine, Node or Bun. A ratio is Sakura's count over hand
JavaScript's: below 1× Sakura retires fewer instructions, above it more. Design §17.109 sets a
ceiling on that ratio for each program family and asks for a median of at most 1.5× over the
fifteen.

## How it is measured

The metric is **instructions retired per call**, read from macOS's `/usr/bin/time -l` on the
reference Mac named above. As with [rustc-perf](https://perf.rust-lang.org), the reason is
repeatability: a count barely moves when other programs share the machine, so the suite runs
while other work goes on and needs no idle night (design §17.264).

<CountFlow />

Each cell is one program at one input size on one engine. The harness calibrates a call count
`k`, then runs five pairs of fresh processes: one calls `run(n)` once, the other `1 + k` times.
Start-up, module loading and the first call's compilation are in both, so their difference over
`k` is the cost of one warm call. The cell is the median of the five pairs. Every program has an
oracle: a cell counts only after it returns the recorded checksum for every input.

Node runs with `--predictable --min-semi-space-size=16 --max-semi-space-size=16`.
`--predictable` keeps V8's garbage collector and compiler on the main thread, so a count does
not depend on how threads were scheduled, and the fixed young generation keeps it from depending
on where the program's files sit on disk (design §17.282).

An instruction count is not a time. It does not see cache misses, branch mispredictions or how
many instructions a core retires per cycle, and two engines can retire the same instructions at
different speeds. Every ratio on this page is a ratio of counts.

### What "advisory" means

A reading is **advisory** when it is reported but blocks nothing. Two kinds are:

- **Bun rows.** Bun's counts spread more than Node's (see [Spread](#spread)), so in a counted
  comparison a Bun row is flagged above 10% and never blocks a change (design §17.265 (5)).
- **Wall times on a loaded host.** The cross-language ceilings are time quantities, so the
  envelope reads them on the wall time of the same runs. The machine was busy while they ran,
  so those times give the direction only (design §17.265 (2)).

The instruction counts themselves are not advisory: they are the baseline every change is
compared with.

### Spread

A cell's spread is (max − min) / median over its five pairs. One outlying pair widens the spread
but barely moves the median, so the last column counts the cells whose middle three pairs also
differ by more than 1%.

## Compile time

One `sakura` process per run after a warm-up, over generated packages and a new project. The
budgets are research/10 §6's, on the p95 of fifteen processes; the targets are design §17.195's,
reported beside the budgets and never an exit. Times are in milliseconds, wall time on the loaded
reference machine, with each case's median instruction count beside them. `test_hello` counts the CLI's own
process, not the Node process it starts.

## The cross-language envelope

Design §17.109 also set ceilings for Sakura's WebAssembly build, on the Node host and on
Wasmtime, against native controls: numeric kernels against Rust and Go, allocation kernels
against OCaml and Koka, handlers against Koka, and the text programs against Rust. Each gating
cell is one program, size, engine and comparison.

<BenchTable table="envelope" />

The envelope is information, not a release gate (design §17.265), and it is far from met.
The native backend, experimental today and in no release, is where that comparison will be made
again.

### Native controls

## Reproduce

On a Mac with the toolchains pinned in
[`bench/toolchains.toml`](https://github.com/icantcodefyi/sakuralang/blob/main/bench/toolchains.toml),
at the commit above:

```sh
bench/bench run --suite js --instructions --json js.json
bench/bench run --suite wasm --instructions --json wasm.json
bench/bench run --suite native --lane matched --instructions --json native.json
bench/bench compile --instructions --json compile.json
bench/bench envelope wasm.json native.json --json envelope.json --md envelope.md
```

Counts from another machine are not comparable with these: a different CPU, OS or engine build
retires different instructions. The baseline files hold every size, every raw count and the wall
time beside it. The procedure that turns a run into a baseline is
[`docs/release.md` §2](https://github.com/icantcodefyi/sakuralang/blob/main/docs/release.md#2-instruction-count-baseline-and-bless).
