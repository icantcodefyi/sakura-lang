This page says which parts of Sakura Lang you can build on and which may still change. Read it
before you depend on Sakura Lang in a script, a CI job or a tool that reads its output.

<Callout type="warn" title="Latest release">
  **Latest release: `v1.0.0-beta.5`.** It is a beta, a preview of 1.0, and **not for
  production**. It may have bugs and may still change before 1.0.0. It is published as a GitHub
  prerelease, on npm under the `beta` tag and as the Homebrew formula `sakuralang-beta`
  ([Install](/docs/install#the-beta)). `npm i -g sakuralang` and `brew install sakuralang`
  still install the earlier preview, `0.1.0`.
</Callout>

## In short

- **Today there is no compatibility promise.** Anything may change before 1.0.0.
- **But breaking changes are listed.** Every breaking change between a beta and 1.0.0 is listed
  in the [changelog](/changelog) with a migration: what to change in your code.
- **From 1.0.0, compatibility holds within 1.x.** Your source code and its standard-library
  calls stay compatible across the 1.x releases.
- **Experimental features carry no promise.** They are opt-in, labelled, and may change or go
  away in any release.
- **Wording is never a contract.** Human-readable output, help text, error message wording and
  generated code can change at any time. A diagnostic's code, fields and fixes are the contract.

## The three levels

Each part of Sakura Lang has one level:

- **Stable**: changes follow the rules below. From `1.0.0-beta.1`, machine-readable
  contracts (diagnostic codes, `--json` records, exit codes and the WebAssembly runtime
  interface) are meant to change only by adding things. During the beta they may still change,
  each with a migration in the changelog. Source and standard-library changes during the beta
  come with a listed migration. From `1.0.0`, source and standard-library compatibility hold
  within a major version (all of 1.x).
- **Experimental**: may change or disappear in any release. You turn it on yourself, and the
  docs label it.
- **Internal**: an implementation detail with no promise, even when you can see it.

## What each part promises

| Part | Level | From |
| --- | --- | --- |
| [CLI](/docs/cli) commands, documented flags, exit codes and environment variables | stable | 1.0.0-beta.1 |
| `build --emit`, `--layout`, `--dump`; hidden switches | experimental or internal | — |
| [`sakura.toml`](/docs/manifest): `[package]`, `[permissions]`, `[verify]`; the `V8005` and `V8006` refusals | stable | 1.0.0-beta.1 |
| [Diagnostic codes](/docs/errors): a code is never reused or renumbered | stable | 1.0.0-beta.1 |
| [`--json` records](/docs/agents/diagnostics#record-kinds): fields are only added within a major | stable | 1.0.0-beta.1 |
| [Standard library](/docs/stdlib) public signatures | stable | 1.0.0-beta.1 with a listed migration; 1.0.0 within a major |
| [`std/worker`](/docs/tour/concurrency#workers-experimental) and the `@worker` attribute; live workers on every target | experimental | — |
| WebAssembly runtime interface (the ABI a WebAssembly module and its Node host share) | stable | 1.0.0-beta.1 |
| The JavaScript backend's internals, generated code, the compiler's internal forms (LIR and Core) and Rust crates, cache files | internal | — |
| [Language server](/docs/editors) standard protocol features | stable | 1.0.0-beta.1 |
| The `sakura/holeContext` language server extension | experimental | — |
| [MCP](/docs/agents/mcp) stdio tools and the snapshot and patch protocol | stable | 1.0.0-beta.1 |
| `--target native` and the native runtime (in the macOS arm64, Linux x64 and Linux arm64 release binaries from v1.0.0-beta.4, and the Intel macOS one from v1.0.0-beta.5) | experimental | — |
| Runtime limits: the JavaScript and WebAssembly hosts read none from the environment; the experimental native driver reads `SAKURA_MAX_HEAP` and `SAKURA_MAX_REQUESTS` | experimental | — |

## When the promises start

The promises above come from [draft RFC 0001](https://github.com/icantcodefyi/sakuralang/blob/main/docs/rfcs/0001-stability-guarantees.md),
a proposal that is not accepted yet. They bind from the release at which the owner accepts
it, and in full from `v1.0.0`. Until then the policy in
[STABILITY.md](https://github.com/icantcodefyi/sakuralang/blob/main/STABILITY.md) applies, and
its inventory is the complete, authoritative list.

## Changes made before the promises start

These changes are already built. They land before the first release that honours the
promises, so they do not count as breaking changes under them:

- **Number literals.** An `Int` literal is in `[0, 2^63 − 1]`; write the minimum as `Int.min`.
  A digit separator `_` goes only between two digits.
- **A source file that is not UTF-8** is a diagnostic,
  [`V0015 source_not_utf8`](/docs/errors/V0015), instead of a usage error.
- **`[permissions] process` is reserved.** `process = []` is accepted and grants nothing,
  the same as leaving the key out. A non-empty list, which 0.1.0 accepted and which also
  granted nothing, is [`V8006`](/docs/errors/V8006).

## After 1.0

Packages arrive in 1.x without breaking existing projects; until then `[dependencies]` is
refused. Native code stays experimental. The current plan, pending the owner's confirmation,
is that native holds up no release and ships as an experimental flag once its test matrix is
green.

After 1.0, a deprecated feature warns, with a migration, for at least two minor releases and
six months before it is removed.
