# First paid agent-DX pilot — 2026-10-18

The discoverable skill condition improved budgeted success from **8/12 to 11/12
for Opus 5.5**, and **8/12 to 9/12 for Sonnet 5.5**. This is a diagnostic pilot,
not evidence of language superiority. All 12 failures stopped at the input cap;
six other capped episodes had accepted final submissions.

The runner counts the **next whole request** before sending it and refuses when
prior input plus that request would exceed 40,000. Thus an episode can stop with
25,415 billed input tokens (Sonnet skill, HTTP); the unspent balance does not prove
it had room for another turn. The next-request counts are absent from the summary.
Tool output retained in history is billed again on later turns.

All **five** episodes recording `prompt --budget 20000` failed at `input_cap`:
Opus baseline tasks 03/04/06/10 and Sonnet baseline task 04. They consumed
32,845–39,305 input tokens. Three episodes recorded `--budget 30000`: Sonnet
baseline 06/10 failed, while 08 succeeded before its cap. Sonnet skill task 04
recorded `--budget 100000` and never submitted. `prompt --budget` is an approximate four-bytes-per-token limit that drops whole
sections; it is not the provider tokenizer or the episode cap. A requested guide
budget is not measured returned tokens: tool-output size and retrieval errors were not retained.
These associations support a retrieval/history bottleneck, not proof that a
particular read caused failure or that a larger cap would ensure success.

Baseline used 583,383 input tokens (median 25,183 per episode); skill used 611,353
(median 29,672.5). Each condition had nine cap terminations. The skill improved
acceptance without reducing total input or cap frequency. Input limits plainly
censor opportunities to implement/repair, but this pilot cannot separate language
learning difficulty, retrieval strategy and budget. Dropping capped episodes would
remove every failure and produce a misleading score.

## What the hard tasks establish

**10-http-validation, 0/4.** The task composes HTTP retrieval, a bounded generic
JSON decoder, a refined record and local typed-failure recovery under a frozen
`Http` row. It requires invalid JSON, out-of-range values, body-size rejection and
failed exchanges to follow the specified fallback behavior. Three episodes never
submitted (Opus baseline 34,019 input; Sonnet baseline 32,091; Sonnet skill 25,415).
Only Opus skill submitted once (36,635 input), ending in `V1002`, `V2002`, `V3001`.
That is consistent with unresolved names, arity mismatches and unhandled failures,
but cannot establish the exact wrong name, call signature or residual row. The
starter checks clean; these final codes describe the submitted change, not a seeded
HTTP diagnostic. Existing gold/oracles show an expressible composition; no evidence
here proves a missing language feature or broken HTTP semantics. The broad stdlib
read did not enable completion within this budget.

**04-local-env-handler, 1/4.** The callback itself carries `Env`, while the outer
signature is pure. Correct behavior requires executing that callback under a local
deterministic handler and returning its actual result; a constant, host lookup or
wider outer row violates the task. Opus skill passed on its first submission after
SKILL.md and stdlib retrieval (36,325 input). Opus baseline and Sonnet skill made
no submission (37,455 and 29,572 input). Sonnet baseline submitted once, ending
with `V1002` (39,305 input). Thus most failures are observed retrieval exhaustion,
not observed incorrect handler implementations. Loss of the seeded `V3001` alone
is not acceptance. The skill's existing generic local-handler example is relevant,
but the summaries cannot prove which text the successful agent used.

**What the skill helped, and what it did not.** Both models newly pass path/import
repair and typed recovery; only Opus newly passes the local-handler task. Opus
pass@1 rises 6→11, Sonnet 6→7. The recovery and handler examples and import guidance
are plausible mechanisms, not isolated causal findings: there was no ablation.
HTTP remains 0/4, Sonnet local-handler still fails, and Sonnet CLI-prefix regresses
from success to no submission. The skill did not remove budget pressure or establish
robust general-purpose agent competence.

   This small generic wording fix accompanies the report and regenerates the mirror

   Treat the resulting bundle as a new intervention, not the evaluated one.
2. **Astra/Sol — documentation follow-up:** audit how compact symbol lookup exposes
   the declaring module, result annotation and failure row, and how it links to
   existing handler/recovery documentation. Prefer navigation improvements over
   another large example dump. Keep examples independent of evaluation tasks;
   do not paste the HTTP or Env solutions into the skill. The current summaries

3. **Designer Fable — diagnostics:** review `V3001` origin/context and whether an
   ordinary effect versus residual `Fail` can lead to a precise existing handler
   or recovery reference. Review `V1002`/`V2002` declaration/argument-count guidance.
   First obtain independent offline reproducers; no language simplification or
   authority-widening fix is justified by these counts. See the dated
   [REQUESTS entry](../../../compiler/REQUESTS.md). Diagnostic-contract or semantics
   changes still require normal design disposition and named maintainer review.
4. **DX5 owner — observability:** split actual structured compiler diagnostics from
   codes quoted in docs; record all lookup identifiers (including `doc`), result
   success/size, remaining aggregate budget and refused next-request input count.
   Preserve privacy by exporting bounded metadata rather than transcript text.
   Add offline replay coverage for these metrics before any new paid study.
5. **DX5 owner — next experiment, only after new authorization:** preflight doc sizes
   offline; compare targeted retrieval and a separately budgeted higher-input arm
   on a fresh paired design, retaining failures and original scores. Recalculate
   worst-case dollars, explicitly approve any new episode/token cap, and keep the
   exhausted ledger intact. The remaining $5.80 is not permission to spend. Multiple
   seeds, additional independently authored tasks and a held-out corpus would be
   needed before claims beyond this pilot; no TS/Python or cross-provider comparison
   was run.

## Limits and review status

There are **12 heterogeneous tasks per cell, one episode per task and one order
seed**. Wilson intervals describe these observations, not representativeness of
all programming tasks. Task pairing is descriptive; there is no paired uncertainty
estimate or replication. The public corpus permits contamination, and unequal
prior model familiarity with syntax/libraries remains uncontrolled.

Raw transcripts were **never uploaded by design**. No provider messages, tool
outputs, patches or per-oracle verdicts are available here, so independent replay,
exact causal diagnosis, retrieval-failure rates and time-to-first-green cannot be
reconstructed. `model_seconds` is model latency, not full episode time or first-green
time. Human review-time samples were not collected. The summary does not export
per-episode starter hashes or refused-request counts; those provenance details
cannot be independently reconstructed from this artifact. Input-cap censoring
is substantial and informative, so this is explicitly a bounded workflow result.

Before copying the summary, its entire JSON structure and every string value were
checked: only run metadata, short document identifiers, diagnostic codes and numeric/
boolean/null metrics were present; no message bodies, source patches, transcript
text, credentials or secret-like key material were found. The committed JSON is
